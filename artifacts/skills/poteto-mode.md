# poteto-mode

> **One-line:** A workflow router that turns coding work into explicit roles, verifiable units, persisted evidence, and bounded handoffs, with small programs for bookkeeping and PR observation.

## Attributes

- **What it does:** Selects a playbook, delegates with concrete acceptance criteria, requires real-artifact verification, and records the state of longer programs. It separates authoring, maintenance to merge-ready, independent verification, and landing. Most authority and quality rules are instructions to agents; the bundled programs implement narrower storage, parsing, observation, and polling mechanisms.
- **Trigger conditions:** “poteto's agent style for concise, detailed responses, deliberate subagents, unslopped prose, simple code, and verified work. Use for poteto, /poteto-mode, or requests to work in this style.” The frontmatter disables model invocation. [[sources/cursor--plugins-pstack#OR01]]
- **Bundled resources:** A 149-line SKILL.md, 23 playbooks, a Bugbot triage reference, an orchestration store and CLI, a PR watcher, a plan checker, dependency bootstrap, worktree audit, and associated tests. This study also covers both plugin agents, Swarm, Poteto Help, and its two references. [[sources/cursor--plugins-pstack#OR01]] [[sources/cursor--plugins-pstack#OR29]] [[sources/cursor--plugins-pstack#OR50]]
- **Progressive disclosure:** Router → selected playbook → leaf skill or reference → helper program. The router requires reading a principle before claiming to apply it. Broad role defaults still occupy the always-loaded router. [[sources/cursor--plugins-pstack#OR01]] [[sources/cursor--plugins-pstack#OR03]]
- **External dependencies:** Cursor-style cloud agents, model selection, task/loop tools, Git, GitHub CLI or Origin, and control skills are assumed by relevant playbooks. The public watcher implements GitHub, not Origin. Tool scripts use Bun and Commander; the package declares TypeScript/Bun types for checks. The audit additionally assumes shell utilities and jq. These dependencies were not installed or integration-qualified by this study. [[sources/cursor--plugins-pstack#OR19]] [[sources/cursor--plugins-pstack#OR29]] [[sources/cursor--plugins-pstack#OR47]]
- **License:** MIT, as recorded for the parent plugin. [[artifacts/plugins/pstack]]

## What problem it solves

Long agent tasks can lose their acceptance criteria, confuse activity with progress, duplicate ownership, or ship code different from what a reviewer tested. Poteto-mode makes those questions explicit at handoffs and separates workflow modes with different authority. Its strongest ideas are the work-unit brief, exact-revision evidence lookup, single ownership of topology, real-surface verification, and explicit incomplete states. These are useful even without adopting its particular model defaults, tone, cloud agent host, or level of ceremony. [[sources/cursor--plugins-pstack#OR05]] [[sources/cursor--plugins-pstack#OR11]] [[sources/cursor--plugins-pstack#OR17]] [[sources/cursor--plugins-pstack#OR18]]

## How it works (mechanism)

The router selects a task-shaped playbook and asks the agent to copy its steps into a todo list, retaining skipped steps with reasons. A one-task autonomous run, a bespoke plan, and a standing program are distinct routes. Within a program, the coordinator externalizes units, evidence, topology, gates, and completion pointers. Workers receive constrained briefs; one actor owns topology; verifiers inspect the actual artifact. A local CLI supports these records but does not spawn workers, enforce role capabilities, or authorize merges. [[sources/cursor--plugins-pstack#OR01]] [[sources/cursor--plugins-pstack#OR05]] [[sources/cursor--plugins-pstack#OR07]] [[sources/cursor--plugins-pstack#OR16]]

The storage implementation uses inspectable TSV/JSON files, a local PID lock, and temporary-file renames. The watcher separates GitHub reads from pure decision logic and emits structured verdicts. The checker turns parts of a Markdown plan contract into deterministic validation. The hard boundary is that a well-formed record, typed readiness object, or successful command is evidence of the helper's local contract, not evidence that the real code was verified, an approval was granted, or a side effect completed exactly once. [[sources/cursor--plugins-pstack#OR08]] [[sources/cursor--plugins-pstack#OR09]] [[sources/cursor--plugins-pstack#OR12]] [[sources/cursor--plugins-pstack#OR21]] [[sources/cursor--plugins-pstack#OR30]]

## What makes it great

It recognizes that a role can outlive its current agent, that a queued merge is not a completed merge, and that a clean check list is not independent user-path verification. It also gives failed, missing, and inconclusive evidence names, so an absent result need not disappear into a favorable summary. The small programs create useful inspection points. Their limitations are equally instructive: vocabulary such as “safe,” “allowed,” and “verified” must be interpreted against the implemented predicate, not taken as a broader guarantee. [[sources/cursor--plugins-pstack#OR03]] [[sources/cursor--plugins-pstack#OR18]] [[sources/cursor--plugins-pstack#OR21]] [[sources/cursor--plugins-pstack#OR32]] [[sources/cursor--plugins-pstack#OR46]]

## What we'd steal

**Priority:** ★★★ is foundational reuse; ★★ is valuable in the matching workflow; ★ is a narrower technique. **Evidence class:** *implementation* means inspected source; *policy* means instructions whose compliance depends on the host and agent; *local check* means the bounded execution recorded below. None means deployed or provider behavior was proved.

### Routing, delegation, and ownership

- **OR01 — ★★★ Route by the work's shape, then disclose only the required procedure.** *Policy.* Separate investigation, feature, bug, performance, experiment, unattended run, and standing program. Copy the chosen steps into the active checklist and leave a reason for each skip. This makes omitted work inspectable without loading every playbook into every task. The portable element is conditional procedure loading, not requiring the same ceremony for a one-line change. A copied todo does not itself prove a step was performed. [[sources/cursor--plugins-pstack#OR01]]

- **OR02 — ★★★ Separate empirical uncertainty from preference and authority.** *Policy.* Observe behavior, timing, layout, or measurement sensitivity through a bounded prototype when that can decide the fork. Keep a cited investigation in its evidence-gathering mode. Reserve human questions for decisions observation cannot settle. Reuse the classification, but scope autonomy explicitly: this router's blanket permission for external chat/tickets/evals is not a substitute for actual user authorization, host permissions, spending limits, or named irreversible-action gates. Its “session overrides” wording is not an implemented permission model. [[sources/cursor--plugins-pstack#OR02]]

- **OR03 — ★★★ Make roles persistent and agent instances replaceable.** *Policy plus agent bootstrap prompt.* Fresh delegates receive the original brief, later directives, prior report, and branch together; reuse is reserved for costly local state or a running process. The parent reviews the diff and owns the summary. Reuse this to avoid lost instructions across interrupted follow-ups. Give children an absolute skill path to preserve version identity: the fallback agent searches installed paths and can choose a different highest version. Fresh context is a handoff technique, not proof of independent judgment. [[sources/cursor--plugins-pstack#OR03]]

- **OR04 — ★★★ Remove shared writes before adding locks.** *Policy.* The Feature checkpoint asks what work truly separates, which state is shared, and what blocks throughput. Give coupled feature work one owner; partition independent audits or disjoint changes. Reuse ownership by file, branch, key, and artifact to reduce coordination load before introducing synchronization. The scripts cannot stop a worker from writing another owner's scope, and maximal parallelism is not the intended goal. [[sources/cursor--plugins-pstack#OR04]]

- **OR05 — ★★★ Use self-contained work-unit briefs and dependency handoffs.** *Policy.* Briefs name goal, scope, context pointers, acceptance, verification, timebox, forbidden changes, reporting, and standing instructions. Small units get small briefs; dependency completion relays concrete context to the next worker. Sampling briefs during the wave catches a weak delegation before all work finishes. Coordinator/worker/verifier roles, delegation-depth and rolling-concurrency limits make capacity explicit, but the CLI is bookkeeping, not a scheduler enforcing those limits or reviewer independence. [[sources/cursor--plugins-pstack#OR05]]

- **OR06 — ★★ Reserve time for integration and process completions at safe points.** *Policy.* Pilot one complete path before scaling, land continuously, and stop new spawning around the stated budget threshold so verification and landing fit. Queue completion messages instead of interrupting the coordinator inside an atomic operation; reconcile every child, including failures and dropouts. Reuse a reserved integration budget and explicit drain points. The source's approximate percentage is a planning heuristic, not measured capacity control; no runtime budget meter stops paid work. [[sources/cursor--plugins-pstack#OR06]]

### State, evidence, and recovery

- **OR07 — ★★★ Separate canonical records from derived status.** *Policy plus implementation.* The program layout assigns units, ledger, frontier, gates, preferences, overview, and inbox distinct jobs. Preserve user preferences verbatim and derive status rather than rewriting another competing account of reality. The store initializes its implemented data files; the fuller prose layout remains a coordinator convention. Reuse inspectable, externally recoverable records, but do not infer that every prescribed overview/decision artifact is automatically created or that local files survive VM loss. [[sources/cursor--plugins-pstack#OR07]]

- **OR08 — ★★ Make the small store boring and inspectable.** *Implementation.* TSV serialization sanitizes tabs/newlines and spreadsheet-formula prefixes; parsing rejects malformed headers/rows. Writes create an exclusive temporary file beside the destination, rename it, then clean up. This is a useful low-dependency local store with straightforward inspection and repair. The guarantee is per-file replacement, not an atomic transaction across units, ledger, frontier, and inbox. There is no fsync protocol here establishing power-loss durability. Validation protects the record shape, not the truth of its contents. [[sources/cursor--plugins-pstack#OR08]]

- **OR09 — ★★★ State exactly what a lock protects.** *Implementation and inferred failure boundary.* An exclusive lock file identifies a local PID; only an ESRCH result establishes a dead process for stale recovery. The force option can remove a live holder. Reuse conservative liveness classification, but add fencing before adopting takeover in a concurrent service: an old holder does not receive a generation token that later writes must validate. The lock is held by a store instance, not a mutex serializing concurrent methods within that instance. Parallel read-modify-write calls can therefore race; this boundary was inferred from source, not reproduced. [[sources/cursor--plugins-pstack#OR09]]

- **OR10 — ★★ Distinguish a flexible work registry from an executable state machine.** *Implementation.* Unit creation checks duplicate IDs and defaults state; updates preserve a simple inspectable table. State values are free strings rather than a declared transition graph. This is convenient for evolving human programs, but it does not enforce prerequisite completion, valid transitions, worker capacity, or one owner per unit. Reuse the registry when operators need adaptable records; introduce a validated state machine only when illegal transitions must become impossible. [[sources/cursor--plugins-pstack#OR10]]

- **OR11 — ★★★ Bind an evidence record to the exact artifact identity.** *Implementation plus stronger policy.* The ledger's lookup key is PR number plus supplied SHA; absence yields NOT-VERIFIED, so a different revision does not inherit the previous row automatically. Reuse this narrow binding. Important limits: SHA is required text, evidence is a required string without artifact validation, verifier is optional, and recording the same key unconditionally replaces the row. The playbook says verifier authority outranks worker self-report; the store does not implement that precedence. It is neither authenticated attestation nor an immutable review history. [[sources/cursor--plugins-pstack#OR11]]

- **OR12 — ★★★ Treat lookup success separately from a passing verdict.** *Implementation.* `orch ledger check` prints the stored verdict and the CLI returns success after a successful command, including when the found verdict is FAIL. Only absence becomes the not-found outcome. A shell condition on exit zero is therefore not a release gate. Ledger summary also counts all stored verdicts, not a join against current PR heads. Reuse typed result handling: consumers must explicitly accept the allowed verdicts at the expected revision and independently establish freshness. [[sources/cursor--plugins-pstack#OR12]]

- **OR13 — ★★ Use a completion inbox, but do not call destructive drain an acknowledged queue.** *Implementation.* Each pointer has a timestamp, agent, unit, status, optional report, and unique filename. Drain reads the batch, renames the directory, recreates the inbox, deletes the drained directory, and returns rows. It cleanly batches local notifications under the store lock. There is no downstream acknowledgement: a crash after deletion but before processing loses those notifications; interruption after rename can strand a batch. Reuse the coordination shape with explicit acknowledge/replay semantics when loss matters. [[sources/cursor--plugins-pstack#OR13]]

- **OR14 — ★★ Derive topology from facts and reject ambiguous linearizations.** *Implementation.* Frontier discovery walks forge base relationships, can see closed/merged parents, and rejects loops, duplicates, and ambiguous branches. Optional pinning checks order/membership; writing the frontier increments a generation. This is stronger than trusting a worker's remembered stack. It still combines local branch SHAs with forge topology without proving local tips equal remote heads or fetching them. Generation is descriptive state, not a fencing token consumed by later writes or merge calls. [[sources/cursor--plugins-pstack#OR14]]

- **OR15 — ★ Observe summaries as summaries.** *Implementation.* Status exposes counts and derived differences for units, verdicts, inbox, gates, and frontier. Reuse a compact operator view to prevent prose status from drifting. Count deltas can hide identity changes: swapping two unit states can leave totals unchanged, and old successful ledger rows remain in aggregate counts. A quiet summary is not proof that the current work, current head, or current evidence stayed the same. Detailed records remain necessary for decisions. [[sources/cursor--plugins-pstack#OR15]]

- **OR16 — ★★★ Recover by reconciling current artifacts before restarting work.** *Policy.* Probe status without accidentally resuming an agent; classify failure; bound repeated retries; externalize work promptly; reconcile late zombie completions against today's frontier. A dead coordinator and a live cloud worker require attachment and inspection rather than duplicate ownership. Use actual side effects as progress evidence, not transcript modification time alone. These are valuable recovery rules, but no durable job engine, idempotency key, exactly-once side-effect execution, or enforced cancellation protocol implements them here. [[sources/cursor--plugins-pstack#OR16]]

### Verification and landing authority

- **OR17 — ★★★ Separate author ownership, topology ownership, verdict ownership, and landing authority.** *Policy.* Autopilot-full uses independent PR owners with root verification under a queue-scoped grant; Autopilot-stack reserves topology to the root and landing to the operator. Owners preserve their work, report every head, and use a lease pinned to the SHA they last controlled. Gate loosening needs independent evidence and a fresh countersign; forge approvals cannot be bypassed. Reuse the role distinctions. A significant limit remains: replacing a stuck owner before its stop lands can leave two capable writers unless the host fences the old one. [[sources/cursor--plugins-pstack#OR17]]

- **OR18 — ★★★ Land only a verified contiguous prefix, then confirm the actual result.** *Policy.* Shipping requires an independent user-path comparison for each PR, stops at the first missing verdict, and freezes scope at that ceiling. A moved revision needs patch-id comparison; carrying a lane across selected nonbehavioral changes additionally requires equivalent build output with documented noise. New changes still need checks and review. Reuse evidence-to-artifact binding and merge readback: queued or auto-merge requested is not merged into trunk. Patch identity alone does not prove equivalence under changed dependencies. No merge wrapper enforces this policy atomically. [[sources/cursor--plugins-pstack#OR18]]

- **OR19 — ★★★ Give PR maintenance explicit modes and a narrower finish line than shipping.** *Policy.* `check` is one pass, `threads-only` addresses comments, `background` avoids blocking the main plan, and `drive` continues to merge-ready. One babysitter owns a stack and must not casually rebase or retarget it. Conflict, thread, and CI triage have an order; one fresh build is permitted for an apparent flake before reclassification. Reuse mode-specific work and cost boundaries. An undeclared drive default can be expensive, and babysitting explicitly supplies no merge authorization. [[sources/cursor--plugins-pstack#OR19]]

- **OR20 — ★★★ Recheck the revision when composing observations from several reads.** *Implementation and inferred boundary.* The watcher reads PR facts, review threads, checks, then potentially commit rollups in separate calls. Looking up the captured head in rollups is useful, but the entire snapshot is not atomic and current-PR check reads are not pinned to that captured head. A push between calls can mix observations. Reuse the separation of reader and decision policy, and add an authoritative head recheck before treating the composition as release evidence. No concurrent-push failure was reproduced in this study. [[sources/cursor--plugins-pstack#OR20]]

- **OR21 — ★★★ Name readiness after the predicate actually computed.** *Implementation contradicting broad documentation wording.* The watcher refuses the merge assessment only for BLOCKED combined with an error/failure rollup. Other merge-state values can be allowed; REVIEW_REQUIRED is not a gate, while CHANGES_REQUESTED is. Code Review Gate is specially exempted for pending/action-required states. READY therefore means the helper found no blocker under its maintenance policy, not that all GitHub approval or protection requirements are met. The playbook's “forge agrees” wording is broader. Never wire this result directly to merge permission without a stronger check. [[sources/cursor--plugins-pstack#OR21]]

- **OR22 — ★★ Fail closed on unavailable evidence and paginate the collections you depend on.** *Implementation.* Check resolution tries the fast path, falls back to paginated GraphQL, and raises unavailable when neither yields checks. Threads are also paginated. Reuse this distinction between “no failing checks” and “could not establish checks.” Limits remain: thread comments request a bounded initial slice and use the initial comment rather than reading the full conversation; malformed pagination with no end cursor ends traversal. A fallback path increases resilience without proving the evidence is complete. [[sources/cursor--plugins-pstack#OR22]]

- **OR23 — ★★★ Model outcomes as discriminated data before formatting them.** *Implementation plus compile-time test source.* Branded PR identifiers, nonempty collections, enumerated external states, and verdict-specific payloads prevent numerous shape mistakes. A READY object must contain the corresponding readiness structure; error, waiting, advance, and complete have distinct payloads. Reuse the typed boundary and pure policy functions. Types establish representability, not the real-world semantics of “allowed”; unsafe interpretations can still inhabit a well-typed object. The compile-time assertions were inspected but their separate strict typecheck was not run. [[sources/cursor--plugins-pstack#OR23]]

- **OR24 — ★★ Make blocker precedence independent of incidental iteration order.** *Implementation.* Stack selection is tier-major: conflicts across the stack precede thread findings, then failing checks and other gates. It reports the PR actually owning the selected blocker or pending work. Reuse explicit precedence as a pure function and test it. This is not the same as only ever considering the lowest PR; the broad stack scan can surface an upper conflict before a lower CI problem. Document that distinction when combining it with a frontier-only work policy. [[sources/cursor--plugins-pstack#OR24]]

- **OR25 — ★★ Poll the active frontier often and the remaining queue less often.** *Implementation.* Queued mode captures PR contexts, maintains cached snapshots, periodically sweeps unmerged entries, and advances only after successful reads. Completed entries drop out; a frontier transition emits ADVANCE. Reuse this resource-conscious state machine. The frozen queue contains PR identities, not immutable SHAs. WAITING/merge-queue means blocker-free but not yet observed merged; it does not prove actual merge-queue enrollment. Wait deduplication keys on PR and counts, so replacing one pending check with another of equal count may not emit a new event. [[sources/cursor--plugins-pstack#OR25]]

- **OR26 — ★★★ Make retry policy explicit, then bound the underlying operation too.** *Implementation.* Query failures get bounded consecutive-error handling and capped exponential backoff; successful reads reset the error streak, and configured deadlines bound waits. Reuse typed failures, retry budgets, and progress-preserving retry state. The subprocess reader has no per-command deadline, so a hung CLI can outlast the polling deadline; default overall timeout is unlimited. There is no jitter in this backoff. Loop bounds and sleep bounds do not automatically bound wall-clock execution. [[sources/cursor--plugins-pstack#OR26]]

- **OR27 — ★★ Include repository identity when inferring branch relationships.** *Implementation.* The watcher excludes fork heads from the local head-name index and prevents upstream children attaching to a fork head. Reuse this guard against same-named branches being mistaken for shared topology. Watcher discovery permits a connected branch traversal, whereas the orchestration frontier requires an unambiguous linear chain; these are different contracts. The watcher's upward traversal lacks its own seen guard. This is a source-level boundary, not evidence of a live GitHub cycle or incident. [[sources/cursor--plugins-pstack#OR27]]

- **OR28 — ★★ Emit one structured verdict stream with a human rendering.** *Implementation.* Versioned records carry sequence, time, mode, and terminal meaning, with JSON default and a pretty renderer derived from the same data. Reuse this to keep automation and human status aligned. Interpret exit codes by mode: a successful status-only snapshot is not READY, just as a successful ledger lookup is not PASS. Schema and semantic versioning should cover changes to predicate meaning, not merely field names. [[sources/cursor--plugins-pstack#OR28]]

### Tooling and plans

- **OR29 — ★★ Fingerprint dependency inputs, but disclose bootstrap side effects.** *Implementation.* Bootstrap hashes package metadata plus the lockfile, checks Commander and an install-key marker, runs a frozen install when needed, then restarts with preserved arguments/environment. Reuse the content-derived invalidation instead of timestamps. This is not an integrity check of every installed dependency and there is no install lock for simultaneous first runs. Importing a CLI, even for help or a nominal read, can initiate installation. Separate setup from observation when offline or no-install execution is required. [[sources/cursor--plugins-pstack#OR29]]

- **OR30 — ★★★ Turn checkable plan requirements into a small deterministic validator.** *Implementation.* Check-plan parses Markdown while excluding fenced code, checks section ordering, checklist structure, fixed verification lanes, screenshot pass predicates, and performance measurement requirements. Reuse syntax checks for requirements that otherwise decay through paraphrase. A structurally valid plan is not an executed plan: unchecked boxes are accepted, evidence artifacts are not verified, and words satisfying a predicate can be empty promises. The fixed multi-lane rubric also needs proportionality when ported to simpler work. [[sources/cursor--plugins-pstack#OR30]]

- **OR31 — ★★ Give each phase a proof plan and keep decision context separate from execution steps.** *Policy.* Multi-phase planning distinguishes plan approval from permission to execute, requires concrete verification on the current head, and includes live surfaces, screenshot predicates, and measurement design. It avoids a meaningless baseline ratio when a feature did not previously exist, permitting absolute budgets instead. Reuse phase contracts, explicit gates, and a readable how-to body with supporting rationale elsewhere. The ten-lane plan is a demanding default, not evidence that every task benefits from ten lanes. [[sources/cursor--plugins-pstack#OR31]]

### Experiments, diagnosis, and evaluation

- **OR32 — ★★★ Declare whether a swarm is partitioning, racing, or comparing.** *Policy.* A partition covers disjoint territory; a race seeks the first valid result; a best-of exercise ranks all candidates. Declare that choice before observing outputs, assign writable scopes or exact revisions, and report every proven finding. Missing and failed lanes remain gaps; one retry does not convert absence into a pass. Reuse this to prevent cherry-picking and duplicate writes. Model-family diversity and independence still depend on actual spawn behavior and host capability, not the prose alone. [[sources/cursor--plugins-pstack#OR32]]

- **OR33 — ★★★ Evaluate behavioral changes with matched, auditable comparisons.** *Policy.* Eval uses sanitized paths, realistic prompts, both variants, blind judging where possible, and saved transcripts/code instead of self-reported success. It scales after an initial small check and requires inspecting outputs. Reuse this as a study design for skills and prompts: the changed instruction must earn its place through observable behavior. No outcome experiment comparing these playbooks was run here, and a blind judge is still a model whose criteria and error modes need scrutiny. [[sources/cursor--plugins-pstack#OR33]]

- **OR34 — ★★★ Calibrate a hillclimb before spending the search budget.** *Policy.* Establish realistic cases, verify metric sensitivity, freeze the harness, and keep baseline and acceptance gates. Try one hypothesis at a time; measure before/after distributions, account for noise and work errors, retain or revert, and log rejected attempts as well as wins. Reuse reproducible search and negative results. A minimum attempt count can create cost after the practical target is already met; carry over the discipline without blindly copying a spending floor. [[sources/cursor--plugins-pstack#OR34]]

- **OR35 — ★★ Use a causal optimization ladder and distinguish numbers from estimates.** *Policy.* Perf issue first traces the bottleneck, then considers removing work, reusing results, reducing, deferring, backgrounding, parallelizing, or making operations cheaper. The reported gain must be tied to matched before/after behavior. Reuse the ladder to avoid optimizing the most visible code rather than the limiting work. A static estimate remains an estimate; one-off performance repair stops at its target instead of silently becoming an open-ended hillclimb. [[sources/cursor--plugins-pstack#OR35]]

- **OR36 — ★★★ Diagnose the real failing surface before designing the fix.** *Policy.* Bug fix starts with reproduction, can create a deterministic trigger, instruments competing hypotheses, narrows the fault, and reverts refuted changes. The same relevant user path must fail before and pass after; wrong-surface and inconclusive evidence do not count. Reuse this to stop speculative architecture fan-out before identifying a mechanism. Red-first testing is valuable when the local target is cheap, but lack of a convenient automated test cannot turn a proxy check into proof. [[sources/cursor--plugins-pstack#OR36]]

- **OR37 — ★★ Freeze the behavior contract before restructuring.** *Policy.* Refactoring names what must remain true, captures behavior where necessary, reduces reader load, migrates callers, and deletes obsolete paths. Reuse characterization and a single coherent migration for internal APIs. Characterization can also pin an existing bug, so the contract must distinguish intended behavior from accidental behavior. The one-wave migration preference is not a safe default for rolling deployments or external consumers that need compatibility. [[sources/cursor--plugins-pstack#OR37]]

- **OR38 — ★★ A prototype answers a question; an investigation produces an evidenced answer.** *Policy.* Prototype isolates a cheap throwaway comparison with enough instrumentation to decide; Investigation reads and explains rather than expanding into implementation. Reuse a declared question, comparison, and disposal boundary. A successful sketch does not demonstrate production correctness, maintainability, or deployment viability. Keeping these modes separate also prevents a read-only research request from becoming unauthorized product work. [[sources/cursor--plugins-pstack#OR38]]

- **OR39 — ★★ Distinguish live instrumentation from analysis of an existing trace.** *Policy.* Runtime forensics diagnoses a running symptom with targeted observation; trace forensics preserves the supplied artifact and turns it into queryable evidence, with uncertainty tied to what the capture can show. Reuse queries and source attribution instead of screenshots of arbitrary hot frames. Instrumentation can alter or perturb a running process even when the deliverable is called read-only. A post hoc trace cannot settle an unsupported counterfactual; propose a paired experiment when needed. [[sources/cursor--plugins-pstack#OR39]]

- **OR40 — ★★ Freeze the visual baseline and shared primitives before parallel parity work.** *Policy.* Visual parity keeps the comparison harness stable and resolves common primitives before delegating components. Reuse this ordering to avoid many independent fixes fighting the same token or layout rule. A pixel-exact threshold is meaningful only under controlled rendering inputs; fonts, platform rendering, animation, and nondeterminism can create differences unrelated to the migration. The policy calls for exact parity but does not supply a universal reproducibility harness. [[sources/cursor--plugins-pstack#OR40]]

### Evidence hygiene and handoffs

- **OR41 — ★★ Author skills as compact decision procedures with source pointers.** *Policy.* Skill authoring composes existing guidance rather than repeating it, tests structural requirements, and treats subjective style checks differently. Reuse prose that changes a decision, references that preserve ownership of facts, and deterministic checks where the contract is mechanical. Indirection can also hide unavailable or drifted dependencies; keep paths/version identity inspectable rather than assuming a named skill resolved correctly. [[sources/cursor--plugins-pstack#OR41]]

- **OR42 — ★★ Investigate comments as claims, while preserving the risk of deleting evidence.** *Agent policy.* Comment-sicko reads nearby code, invokes How/Why for non-obvious claims, checks suppression rules, and retains narrow legal/public-contract/external-constraint exceptions. It confines edits to comments and flags exact symbols for later reshaping. Reuse the demand to verify stale rationale. Its deletion-on-uncertainty rule is an evidence-loss risk: a valid but unproved constraint can disappear before any structural replacement exists. A MUST KILL flag is an open refactor request, not proof the underlying risk was resolved. [[sources/cursor--plugins-pstack#OR42]]

## Open questions / what's unclear

- Can a pinned supported Bun/toolchain pass the full orchestration, CLI, and compile-time suites offline, including process-exit and environment-substitution behavior?
- Should ledger consumers have a dedicated fail-closed passing-verdict command, authenticated verifier identity, and append-only history rather than overwrite semantics?
- What fencing and acknowledgement protocol would make force takeover, worker replacement, and inbox consumption safe across crashes and overlapping writers?
- Should readiness explicitly require current-head stability, required review approval, and complete forge protection state, with an accurate name for the narrower existing predicate?
- Which workflow rules materially improve quality or time-to-review under controlled evaluation, and which add costly ceremony without improving the outcome?
- How can comment cleanup retain useful unproved constraints until the proposed structural replacement is reviewed and implemented?
