# statechart

> Turn a checked behavioral model into a reviewable chart and counterexample stories, while preserving the distinction between the model, the code, and the promise being checked.

This is a deep study of `statechart` and pstack's specialized verification family at commit `9580c23696ac8d7abed0c166f2f9918800afb819`. The companion skills `create-verification-skill`, `maintain-verification-skill`, `create-formal-verification-skill`, `maintain-formal-verification-skill`, `benchmark-checklist`, and `tdd` are **separate skills**, not modules bundled inside statechart. ## What problem it solves

A raw model-checker trace is difficult for the person who owns behavior to assess, especially when an application screen hides the state that caused a race or incorrect side effect. A green check can also remain green after the implementation changes underneath its model. The family tackles both problems: explain the formal result in observable terms, and preserve a maintenance discipline that reconnects the verifier to source before trusting it. Neither readable output nor model-checker success alone proves the live application correct. [[sources/cursor--plugins-pstack#VE10]] [[sources/cursor--plugins-pstack#VE13]] [[sources/cursor--plugins-pstack#VE14]]

## How it works

### Select evidence that can answer the claim

The real-app generator discovers launch, driving, observations and isolation from the repository, then writes a skill and feature map that another agent can use cold. Its proof standard includes actual user entry points, action-plus-result evidence, independent side effects, doctor checks and cleanup that preserves artifacts. Creation trials one feature; maintenance requires every feature, with concurrent source readers and one coordinator controlling live interaction. Doc drift, harness shortcomings and product regressions have different remedies. These are prompt contracts, not an implemented universal driver. [[sources/cursor--plugins-pstack#VE01]] [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE03]] [[sources/cursor--plugins-pstack#VE05]] [[sources/cursor--plugins-pstack#VE06]]

The formal generator chooses consequential properties ordinary tests rarely reach. It chooses a model checker for ordering questions, a code verifier for appropriate code-level properties, generated inputs against real code when no verifier fits, and a proof when the desired guarantee exceeds useful finite bounds. A model must cite its code and preserve the code's atomicity. The generated check must catch a deliberate real-code break before handoff. Maintenance repeats that sensitivity check after reconciling source changes, and changes a property only when evidence says the promise intentionally changed. [[sources/cursor--plugins-pstack#VE07]] [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE09]] [[sources/cursor--plugins-pstack#VE11]]

### Keep source, model, property and chart authority distinct

`from-spec` starts from a model; `from-chart` creates a skeleton from an agreed Mermaid chart. Existing generated `.tla` files are preserved on rerun so added implementation guards are not discarded; the command compares their resulting reachable machine with the original chart. Each region becomes a variable, and identically labeled events synchronize eligible regions. Unsupported Mermaid constructs are refused. A `--against` spec uses its own config, while `--fixed` can inherit the current config if its sibling is absent; missing comparison rules are reported rather than assumed checked. [[sources/cursor--plugins-pstack#VE13]] [[sources/cursor--plugins-pstack#VE18]] [[sources/cursor--plugins-pstack#VE19]] [[sources/cursor--plugins-pstack#VE45]]

Every invariant runs separately so one failure does not mask another. Broken invariants rerun with one worker for stable shortest model paths. A later graph run marks every invariant violation on the explored states. PROPERTY formulas run separately: temporal failures have raw counterexamples and looping-state explanations, while the chart colors concern invariants. Deadlock checking is explicitly disabled because quiescence is allowed; progress must be expressed by appropriate properties and assumptions. These are checks on the supplied model/configuration, not theorem proofs about arbitrary code. [[sources/cursor--plugins-pstack#VE16]] [[sources/cursor--plugins-pstack#VE28]] [[sources/cursor--plugins-pstack#VE46]]

A JavaScript mapping supplies reader labels, actions, causes, optional groups and developer detail. The tool preserves reader actions, changes affecting a rule, and the breaking step in stories; it names omitted steps and alternative ways into the bug. Coarse labels receive mixed/after/worse status when warranted. Schema guards prevent the second model's missing fields from becoming misleading labels, and tuple adapters keep TLA's one-based indexing explicit. Comparison replay explains the first divergence on a bug path; it is not a general bisimulation or implementation-refinement proof. [[sources/cursor--plugins-pstack#VE20]] [[sources/cursor--plugins-pstack#VE21]] [[sources/cursor--plugins-pstack#VE22]] [[sources/cursor--plugins-pstack#VE23]] [[sources/cursor--plugins-pstack#VE24]] [[sources/cursor--plugins-pstack#VE30]]

`--cover` reports what its smaller overview omits. Parallel-region layouts are accepted only when they reconstruct the flat projected graph and preserve status; reduced arrows are checked for invented transitions and corrected or abandoned. Group colors cannot override verifier status. Guard words and timer annotations remain human-reviewed explanations: their prose and durations are not checked by TLC. The “proof” of a region layout is a consistency check against the tool's projection, not proof that the underlying model describes production. [[sources/cursor--plugins-pstack#VE25]] [[sources/cursor--plugins-pstack#VE26]] [[sources/cursor--plugins-pstack#VE27]] [[sources/cursor--plugins-pstack#VE42]]

### Preserve the evidence through failure and change

The runner snapshots recognized specification/configuration/mapping dependencies, checks copied models/configs with TLC and compares input contents again before rendering/publication. The mapping is still imported from its live path, so transient edits restored before the final checks are outside a stronger immutable-rendering guarantee. It stages complete outputs and refuses directories containing unfamiliar filenames. On normal renaming filesystems it replaces the output as a unit, while the documented copy fallback has weaker concurrency properties. Valid narrower findings survive later analysis or rendering failures in named scratch output; incomplete exploration is warned about. Exit 0 means the configured expectations matched, which can include known-broken rules; it does not always mean all rules held. ## What makes it great

The strongest contribution is its insistence that a check can be wrong even when it passes. It pairs the everyday discipline of real-path, side-effect evidence with formal modeling obligations, then makes failures readable without hiding the difference between model behavior and application behavior. The executable tool also tests its own presentation and publication machinery: it reports mixed projections, missing comparison rules, omitted chart states and stale inputs. Those mechanisms are valuable precisely because the limits remain visible; the local help-output failure is a reminder to apply the same standard to the verifier. ## What we'd steal

★ marks the highest-value portable ideas; breadth is retained. Every item names what to reuse and a constraint on the claim.

### Build a verification driver from the real product

1. ★ **Interview the repository before the user (P).** Discover surface, launch, driving, evidence and isolation from source and existing harnesses. Reuse this five-part intake for unfamiliar applications; ask only what is genuinely unobservable. Repository claims still need execution, especially startup instructions. [[sources/cursor--plugins-pstack#VE01]]
2. **Choose the primary surface while acknowledging the rest (P).** A web app can also expose CLI/API routes. Name which surface the generated driver owns so a convenient endpoint does not quietly stand in for the user's actual path. Secondary surfaces remain separate coverage work. [[sources/cursor--plugins-pstack#VE01]]
3. **Prefer the project's existing harness and startup contract (P).** Reuse Playwright specs, PTY helpers, documented scripts and health signals before inventing controls. This lowers maintenance cost but inherits their blind spots; an existing harness is a starting point, not proof of coverage. [[sources/cursor--plugins-pstack#VE01]]
4. ★ **Define readiness as usability, not process liveness (P).** Launch from an empty data directory through migration, seeds and authentication. A health endpoint responding while initialization is incomplete is insufficient. Reuse a concrete readiness predicate for every automated driver. [[sources/cursor--plugins-pstack#VE02]]
5. **Make the doctor establish instance identity (P).** Check version/build, process, owned port and auth before acting. This is a targeted precondition check, not a universal diagnosis: healthy processes can still have wedged UI state. [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE06]]
6. **Choose the session lifecycle that matches the surface (P).** Servers can use one long-lived instance; short-lived CLIs need a fresh isolated PTY/session per drive. Encode that distinction in the generated skill so maintenance does not impose an unsuitable lifecycle. [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE06]]
7. **Establish isolation before parallel driving (P).** Give instances distinct ports, data directories and profiles; explicitly refuse double-driving shared state. Parallel source reading is useful even when live control must remain serial. [[sources/cursor--plugins-pstack#VE01]] [[sources/cursor--plugins-pstack#VE03]] [[sources/cursor--plugins-pstack#VE06]]
8. ★ **Prove the action, outcome and independent side effect (P).** Capture the user action and resulting state, then confirm persistence or other effects through a second user-facing/read-only view. A success toast or final screenshot alone is weak evidence. Do not substitute internal setters or test-only endpoints for the path under test. [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE04]]
9. **Measure what a dry-run actually skips (P).** Inspect files, network and Git refs instead of trusting the mode's name. Use this when a verification route claims to be inert; the skill's rule is observational, not an automatic sandbox. [[sources/cursor--plugins-pstack#VE02]]
10. **Prefer stable handles and state predicates (P).** Use ARIA roles, accessible names, CLI JSON and route paths; wait for completed result/empty states rather than fixed sleeps. These handles can drift, so the map and doctor need maintenance. [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE04]]
11. **Keep cleanup ownership narrow and evidence durable (P).** Kill only instances the run started; remove disposable data but preserve proof artifacts. Verify evidence still exists after cleanup, including failed iterations. This makes teardown part of correctness, not an afterthought. [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE03]] [[sources/cursor--plugins-pstack#VE06]]
12. **Treat verification scaffolding as explicitly temporary (P).** If irrelevant missing fixtures block startup, name any scaffolding and remove it afterward. A broken base must be repaired or reported rather than fossilized into an instructional skill. This exception does not authorize masking application defects. [[sources/cursor--plugins-pstack#VE01]]

### Make coverage a maintained feature inventory

13. ★ **Write the handoff for an agent reading cold (P).** Include exact commands, registered frontmatter, executable helpers, invocations and proof locations without placeholders. A helper that must be reverse-engineered is unfinished. The generator's actual output still needs a live trial. [[sources/cursor--plugins-pstack#VE02]] [[sources/cursor--plugins-pstack#VE03]]
14. **Use a feature index plus one recipe per feature (P).** Keep user-facing subfeatures, every entry point, driving instructions and gotchas in a compact fixed structure. The source seeds only three to five features; this is an extensible inventory, not immediate whole-product coverage. [[sources/cursor--plugins-pstack#VE03]] [[sources/cursor--plugins-pstack#VE04]]
15. ★ **Do not substitute one entry point for another (P).** A feature exposed through a toolbar, keyboard shortcut and CLI has distinct journeys. Record feature ID and entry point with evidence; a skipped route is not verified because another works. [[sources/cursor--plugins-pstack#VE03]] [[sources/cursor--plugins-pstack#VE04]]
16. **Preserve failed preconditions rather than weakening journeys (P).** Missing seed data, entitlement or external state becomes a documented prerequisite and precise unreachable result. Keep the intended path intact so a passing run cannot be bought by erasing the hard case. [[sources/cursor--plugins-pstack#VE03]] [[sources/cursor--plugins-pstack#VE06]]
17. **Require an end-to-end proof of the generated instructions (P).** Creation must launch, doctor, drive one mapped feature, capture evidence and clean up. One trial proves basic usability of the skill, not full feature coverage; unexecuted output remains a draft. [[sources/cursor--plugins-pstack#VE03]]
18. **Account for stand-in environments explicitly (P).** If a container substitutes for a VM, list setup steps the substitute performed that the real target will not. Those steps remain unverified. Reuse this as a precise transferability ledger instead of a vague “tested locally.” [[sources/cursor--plugins-pstack#VE03]]
19. ★ **Parallelize source reading and serialize live control (P).** Maintenance assigns one read-only reader per feature; the coordinator reconciles recipes and owns driving. This combines broad investigation with one accountable mutator, avoiding multiple agents disturbing the same state. [[sources/cursor--plugins-pstack#VE06]]
20. **Reconcile coverage before expanding it (P).** Repair index drift, require every feature summary, merge overlapping recipes, then inspect recent churn for missing user surfaces with concrete source paths. The workflow explicitly avoids re-proving every clean sentence. [[sources/cursor--plugins-pstack#VE06]]
21. **Re-doctor after surprises and re-prove harness fixes (P).** Failed drives trigger health checks; a healthy-but-wedged UI requires reset/relaunch. Skill drift permits one scoped retry before blocked status. Harness corrections must be driven live before shipping. [[sources/cursor--plugins-pstack#VE06]]
22. ★ **Separate doc drift, harness gap and product defect (P).** Maintenance edits only its verification directory. Update an obsolete description, fix a driver that cannot reach working behavior, but report genuinely broken application behavior separately. This prevents “verification maintenance” from silently changing the product or documenting away a regression. [[sources/cursor--plugins-pstack#VE05]] [[sources/cursor--plugins-pstack#VE06]]
23. **Give maintenance honest terminal outcomes (P).** Clean requires complete source and live feature coverage; changed produces one proven correction set; blocked names unfinished coverage or shipping impediments. Concise scratch run notes do not become permanent product clutter. [[sources/cursor--plugins-pstack#VE05]] [[sources/cursor--plugins-pstack#VE06]]

### Match formal methods to the question

24. ★ **Select targets by harm and test blind spots (P).** Seek a consequential promise where interleavings, rare inputs or unsafe behavior evade ordinary tests. Do not pick the easiest toy model merely to claim formal verification. This remains expert/agent judgment, not a computed risk score. [[sources/cursor--plugins-pstack#VE07]]
25. **Let the claim choose the verification technology (P).** Event order suggests a small model checker; all-input code properties suggest a code verifier; all-size claims may need proof. If the language lacks a verifier, generated-input tests should exercise real code rather than a hand-reimplemented function. [[sources/cursor--plugins-pstack#VE07]]
26. ★ **Name model checking, bounded verification and proof accurately (P/S).** State scope, constants, assumptions and omissions. A TLC pass checks reachable behavior of the supplied model/configuration, not all possible deployments; this bundle is not a theorem prover for arbitrary production code. [[sources/cursor--plugins-pstack#VE07]] [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE16]]
27. ★ **Match atomic model actions to atomic implementation steps (P).** Cite the real file/function behind variables, guards and actions. Merging two racy code operations into one indivisible modeled step can prove away the bug. Reuse atomicity review as a first-class modeling obligation. [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE11]] [[sources/cursor--plugins-pstack#VE13]]
28. ★ **Demonstrate that every property can fail (P).** Remove a guard or reorder a real-code step, run the generated instructions and require detection, then restore the baseline. This is a fault-injection sanity check on the verifier, not an exhaustive mutation score. [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE09]]
29. **Keep findings independent of the desire for green output (P).** If current code breaks the property, retain the counterexample and report the harm. Do not weaken the property/model or patch product code merely to hand over a passing result. [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE09]] [[sources/cursor--plugins-pstack#VE10]]
30. **Record a cheap, reproducible rerun contract (P).** Give one command, tool version, covered files/functions, bounds, assumptions and last-confirmed commit. Cheap checks are more likely to be reused, but low cost must not be obtained by hiding a weaker bound. [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE09]]
31. **Reference a companion skill by stable name, not volatile internals (P).** Generated TLA+ verification skills delegate result reading to `/statechart`; they must not copy its machine-specific paths/options. This reduces duplicated interface knowledge while relying on the named dependency being available. [[sources/cursor--plugins-pstack#VE09]]

### Keep the verifier aligned with evolving code

32. ★ **Treat a stale green pass as a dangerous result (P).** Run the old check before updating it to preserve a baseline, then independently reconcile covered code. A pre-update pass says the old description still holds; it does not certify the current implementation. [[sources/cursor--plugins-pstack#VE10]] [[sources/cursor--plugins-pstack#VE11]]
33. **Classify changes before changing the model (P).** Separate no semantic effect, representation drift, intentional promise change and possible regression. Check this against model/code rather than trusting a commit message. A property change needs explicit evidence of intended behavior change. [[sources/cursor--plugins-pstack#VE11]]
34. **Follow moved code and new writers of guarded state (P).** Coverage survives renames/splits; newly added functions modifying the same fields can invalidate an old proof. Reuse semantic dependency discovery instead of a literal path-only diff. [[sources/cursor--plugins-pstack#VE11]]
35. ★ **Update from source before seeing the new result (P).** Rebuild the model/harness from the changed implementation, then rerun. Document old and new property wording plus evidence; disclose any bound reduction. This creates a barrier against fitting the verifier to the desired result. [[sources/cursor--plugins-pstack#VE11]]
36. ★ **Replay counterexamples against reachable real entry points (P).** If a model step cannot occur in code, repair the model; if all can occur, report a bug and its introducing commit. Direct tests are strongest; mixed execution/source evidence and copied-code reproductions must disclose their limits. [[sources/cursor--plugins-pstack#VE11]] [[sources/cursor--plugins-pstack#VE14]]
37. **Re-challenge passing checks after reconciliation (P).** A changed model can accidentally lose sensitivity. Repeat a targeted broken variant after a pass, not only during initial generation. A successful mutation probe does not prove complete coverage, but it rules out one silent-loss mode. [[sources/cursor--plugins-pstack#VE11]]
38. **Advance the sync commit only after reconciliation (P).** Blocked checks retain their old sync commit; updated checks may still legitimately report a bug. Ship verification updates separately from product fixes so reviewers can see what the evidence apparatus changed. [[sources/cursor--plugins-pstack#VE10]] [[sources/cursor--plugins-pstack#VE11]] [[sources/cursor--plugins-pstack#VE12]]
39. **Report both representation status and behavioral status (P).** “Updated and bug” is a valid outcome. Keep drift, inability to run, intentional new promise and true counterexample distinct; a single pass/fail bit loses the reason work is required. [[sources/cursor--plugins-pstack#VE10]] [[sources/cursor--plugins-pstack#VE11]] [[sources/cursor--plugins-pstack#VE12]]

### Make formal results readable without changing their authority

40. ★ **Give the human reader a behavioral projection (P/I).** State names express what users/operators/reviewers observe or care about; events describe what happens. Reader and developer views can coexist. Labels must include hidden-but-important effects such as double charging; readability must not erase a decisive variable. [[sources/cursor--plugins-pstack#VE13]] [[sources/cursor--plugins-pstack#VE14]] [[sources/cursor--plugins-pstack#VE20]]
41. **Use chart-first and spec-first as separate entry modes (P/I).** Chart-first helps owners agree on behavior before code exists; spec-first inspects concrete implementations/designs. Once guards and variables enrich a generated spec, keep that spec and compare it back to the agreed chart rather than regenerating away the edits. [[sources/cursor--plugins-pstack#VE13]] [[sources/cursor--plugins-pstack#VE15]] [[sources/cursor--plugins-pstack#VE18]]
42. **Model independently changing parts as regions (P/I).** Each region becomes a variable; identical labels denote one event moving every enabled region, while other regions stay. This is a deliberate synchronization semantics, not arbitrary interleaving of identically named events. [[sources/cursor--plugins-pstack#VE18]] [[sources/cursor--plugins-pstack#VE19]]
43. **Turn reader promises into explicit invariants (P/I).** One `%% never` rule generates a named invariant with its human sentence. Include a variable for any outcome the rule requires rather than dropping the rule because the model cannot express it yet. [[sources/cursor--plugins-pstack#VE14]] [[sources/cursor--plugins-pstack#VE15]] [[sources/cursor--plugins-pstack#VE18]]
44. **Search for a reachable goal by breaking its negation (P/I).** A “goal never happens” invariant plus expected-break status turns a shortest counterexample into a path to the goal. Label this clearly: generated stories still call it a bug, and reachability is not inevitability. [[sources/cursor--plugins-pstack#VE14]] [[sources/cursor--plugins-pstack#VE17]]
45. ★ **Check each invariant independently (I).** Separate TLC runs prevent the first failing invariant from obscuring another. Add each rule as a constraint to stop its paths at the first violating state, then separately dump the full graph and mark all broken invariants. This is model analysis, not code execution. [[sources/cursor--plugins-pstack#VE16]] [[sources/cursor--plugins-pstack#VE46]]
46. **Use parallel exploration, deterministic counterexample replay (I).** Initial checks use automatic workers; broken invariants rerun with one worker to obtain stable shortest model paths. Chart bug classes then choose fewest reader steps among obtained traces. Do not call that a globally optimized shortest path under every possible reader abstraction. [[sources/cursor--plugins-pstack#VE16]] [[sources/cursor--plugins-pstack#VE20]]
47. ★ **Keep temporal properties separate from state-invariant charts (I).** Each PROPERTY gets a run; broken temporal formulas point to their raw TLC traces and summarized repeating states. Detect non-temporal PROPERTY formulas checked only initially and recommend INVARIANT when every state matters. A chart with no red states can still have a failed temporal property. [[sources/cursor--plugins-pstack#VE16]] [[sources/cursor--plugins-pstack#VE28]]
48. **Group bug classes by rule and cause, retaining concrete counts (I).** A cause distinguishes failures ending on the same screen; absent cause falls back to final reader state. Preserve model steps, reader steps and concrete counterexample counts so a concise narrative is not mistaken for the whole state space. Cause quality remains mapping-author judgment. [[sources/cursor--plugins-pstack#VE20]] [[sources/cursor--plugins-pstack#VE25]]
49. **Keep steps that carry causal evidence visible (I).** Retain reader actions, label changes, changes to variables read by the rule, and the breaking step; count/name hidden steps. Also list distinct steps into a bug so the shortest story does not imply a unique cause. Static read inference has language-subset limitations. [[sources/cursor--plugins-pstack#VE20]] [[sources/cursor--plugins-pstack#VE30]]
50. ★ **Represent mixed and downstream states honestly (I).** A label can contain both a clean reachable state and a violating state; mark it mixed. A state reachable only after a violation is “after,” not healthy. A proposed fix can introduce a new “worse” state. These statuses resist misleading coarse projections. [[sources/cursor--plugins-pstack#VE21]]
51. **Report where a proposed fix changes the story (I).** Replay the bug's actions and shared state on the second model; show the first different outcome or disabled step. Report “same states, rule not checked” separately from “same states, rule holds.” This is an explanation algorithm, not a general refinement proof. [[sources/cursor--plugins-pstack#VE22]] [[sources/cursor--plugins-pstack#VE45]]
52. **Require a shared observation schema for comparisons (I).** Guard mapping access when a model lacks a variable/field or exposes incompatible types; allow explicit existence checks and report missing fields. Do not generate confident “undefined” labels that look like real system states. [[sources/cursor--plugins-pstack#VE23]]
53. **Preserve source-language indexing at the mapping boundary (I).** TLA tuples are one-based and index zero throws; array methods/spread remain available with their documented zero-based callback semantics. Explicit adaptation catches a common off-by-one error but adds a proxy layer that itself needs tests. [[sources/cursor--plugins-pstack#VE24]]
54. **Keep visual omissions auditable (I).** `--cover` retains routes to settled states and every bug path and lists omitted states/transitions. It falls back to full coverage when reader actions are absent. Counts retain their documented scope, so picture size is not confused with checked-state count. [[sources/cursor--plugins-pstack#VE25]]
55. ★ **Validate a compressed presentation against its underlying graph (I).** Parallel-region rendering is accepted only when the reconstructed reachable labeled machine matches the flat projection and preserves status. Reduced arrows must not invent transitions; otherwise add necessary arrows or fall back. This validates presentation relative to the projection, not model fidelity to real code. [[sources/cursor--plugins-pstack#VE26]]
56. **Do not let aesthetic grouping override verifier status (I).** Mapping groups cannot use status names; ambiguous groups remain ungrouped, dark fills are rejected, and violations keep strong visual status signals. The color layer helps review but does not independently validate labels or properties. [[sources/cursor--plugins-pstack#VE27]] [[sources/cursor--plugins-pstack#VE48]]
57. **Separate annotated guards/timers from checked semantics (I/P).** Textual `guard()` descriptions and `timer()` seconds improve explanation, but TLC does not check those annotations or run a real clock. Reviewer inspection must connect them to code; syntactic numeric validation is not timing verification. [[sources/cursor--plugins-pstack#VE42]]

### Preserve trustworthy execution and failure records

58. ★ **Keep “as expected,” “behavior differs,” and “could not finish” separate (I).** Exit 0 can mean all rules pass or the exact named known-broken set remains; exit 1 means changed behavior/unexpected results; exit 2 means incomplete operation. Consumers must read the expectation policy, not interpret zero as universal correctness. [[sources/cursor--plugins-pstack#VE17]]
59. **Preserve reference configuration authority (I).** `--against` requires the spec's own configuration; `--fixed` may use its sibling config or inherit the current one. Warn when a comparison omits a rule and identify known failures declared in neighboring configs. Configuration is part of the verification claim. [[sources/cursor--plugins-pstack#VE45]]
60. ★ **Bind analysis to copied input contents (I/O).** Snapshot specifications, configs, mapping and recognized local dependencies; TLC checks copied models/configs, and contents are compared again before rendering/publication. Changes in timestamps/inodes alone do not invalidate results. Mapping imports still use the live path, so the snapshot does not bind every rendering input immutably. [[sources/cursor--plugins-pstack#VE31]] [[sources/cursor--plugins-pstack#VE50]]
61. **Stage complete outputs and protect foreign files (I/T).** Work in scratch, replace an output directory only if its contents match the tool-owned namespace, and restore the previous folder after publication failure when possible. The non-rename fallback is explicitly weaker under concurrency; ownership is name-based, not cryptographic provenance. [[sources/cursor--plugins-pstack#VE32]]
62. **Keep useful failure evidence when the rest cannot finish (I).** A found counterexample survives later TLC errors; emit a warning that exploration was incomplete. Mapping/rendering failure preserves TLC output in a named scratch folder. Missing chart output must not erase the valid narrower finding. [[sources/cursor--plugins-pstack#VE34]] [[sources/cursor--plugins-pstack#VE44]] [[sources/cursor--plugins-pstack#VE47]]
63. **Separate analysis success from rendering success (I).** Require every requested PNG to render for overall success, retain nonvisual artifacts, and cap raster size. Charts are review deliverables with their own failure mode; no PNG does not imply no checked result. [[sources/cursor--plugins-pstack#VE17]] [[sources/cursor--plugins-pstack#VE27]] [[sources/cursor--plugins-pstack#VE48]]
64. **Version tools and isolate their configuration (I).** Pin TLC to an immutable release/checksum, use an empty mise working directory, and cache exact renderer package versions. This reduces ambient configuration interference. Initial installation still requires network; pinned top-level packages are not a fully hermetic environment. [[sources/cursor--plugins-pstack#VE33]]
65. **Bound graph/output resource consumption without erasing rule results (I).** Stop at Node's maximum readable string size, preserve already printed results and distinguish “cannot draw” from “property passed.” This avoids silently truncated graph claims; smaller constants change the verified scope and must be disclosed. [[sources/cursor--plugins-pstack#VE34]] [[sources/cursor--plugins-pstack#VE47]]
66. **Test the evidence tool's own failure paths (T/O).** The suite exercises malformed charts, missing configs, unknown arguments, absent dependencies, interrupted checks, stale inputs, renderer failures, filesystem races and schema mismatches. The test inventory is broad, but optional dependencies gate many tests and only the offline subset was run here. [[sources/cursor--plugins-pstack#VE37]] [[sources/cursor--plugins-pstack#VE38]] [[sources/cursor--plugins-pstack#VE39]] [[sources/cursor--plugins-pstack#VE40]] [[sources/cursor--plugins-pstack#VE43]] [[sources/cursor--plugins-pstack#VE44]] [[sources/cursor--plugins-pstack#VE47]]
67. **Use structure checks to keep the tool reviewable (T).** A test caps each top-level script at 1,000 lines and asks for cohesive extraction. This is a maintainability prompt encoded as a test, not evidence that functions are simple or modules well-factored. [[sources/cursor--plugins-pstack#VE40]]

### Verify the meaning of performance and regression evidence

68. ★ **Write the exact performance claim before measurement (P).** Define unit, dataset, percentile and user-facing interpretation; inspect what the harness times/counts/ignores. This narrows what the evidence must support and exposes misleading summaries before optimization begins. [[sources/cursor--plugins-pstack#VE35]]
69. **Find the limiter without contaminating the reported run (P).** Profile separately, map the hotspot to source and watch whether the load generator saturates first. Without a limiter, an apparent speedup remains inconclusive under this checklist. This is a demanding heuristic, not a mathematical necessity for every descriptive measurement. [[sources/cursor--plugins-pstack#VE35]]
70. **Compare realistic tuned configurations and physical limits (P).** Use production flags, pool/cache/batch settings and common data; check bandwidth/core/Amdahl-style bounds. A large improvement outside plausible limits can indicate a no-op, rejected work or changed workload rather than an optimization. [[sources/cursor--plugins-pstack#VE35]]
71. ★ **Count correct completed work inside the timed region (P).** Count errors and validate outputs, confirm requests/rows/bytes actually ran, and await lazy work. These checks apply even to a one-run ballpark; faster rejection is not throughput improvement. [[sources/cursor--plugins-pstack#VE35]]
72. **Interleave repeated measurements and connect micro to end-to-end (P).** At least five alternating runs per side, median and range, realistic sizes/concurrency, and a whole-path measurement reduce warmup/drift and significance errors. The source's “smaller than variation” rule is a heuristic; statistical design still requires judgment. [[sources/cursor--plugins-pstack#VE35]]
73. **Preserve an inconclusive verdict (P).** Untuned comparisons, unknown limiters, unchecked failures or unconfirmed work block a winner declaration. Link detailed runs while leading with one actionable number. This avoids pressuring measurement into a persuasive result. [[sources/cursor--plugins-pstack#VE35]]
74. ★ **Use failing-before/passing-after evidence when the test is cheap and meaningful (P).** TDD selects the narrowest existing executable target, proves failure for the intended reason, makes a small fix and reruns. It encodes desired behavior rather than mirrors the implementation. [[sources/cursor--plugins-pstack#VE36]]
75. **Prefer the closest useful check over a bad new test (P).** Explicitly skip brittle mocks, expensive unrelated harness construction or tests coupled to accidental internals. Use focused scripts, browser automation or manual reproductions and disclose missing failing-before evidence. This is proportional rigor, not permission to declare an unverified fix complete. [[sources/cursor--plugins-pstack#VE36]]


## Negative findings and limits


1. **Observed piped-help truncation, scoped to this environment.** Node v23.6.1 on this macOS host returned exit 0 but only 8,192 bytes from `statechart.mjs --help`; importing HELP gives 25,747 expected bytes including newline. The source's test at lines 1625–1638 failed because the Exit codes section was absent. The CLI uses `console.log(help)` followed by immediate `process.exit(0)` at 894–896. This is consistent with unflushed pipe output; it is not a failure of TLC or model logic. [[sources/cursor--plugins-pstack#VE38]] [[sources/cursor--plugins-pstack#verification-local-checks]]
2. **Interruption preserves published outputs but can leave TLC alive.** The inspected integration test deliberately SIGTERMs the parent and asserts the TLC process group outlives it before manually killing it. The runtime does not install a parent-signal child cleanup handler in the inspected path. This is a lifecycle limitation, not an atomic-publication defect. Not executed locally. [[sources/cursor--plugins-pstack#VE43]]
3. **No universal proof or production refinement certificate.** The executable tool checks supplied TLA+ models/configs and renders projections; handwritten model fidelity and real-code replay remain human/agent obligations. A correctly checked inaccurate model still yields inaccurate conclusions. [[sources/cursor--plugins-pstack#VE07]] [[sources/cursor--plugins-pstack#VE08]] [[sources/cursor--plugins-pstack#VE09]] [[sources/cursor--plugins-pstack#VE10]] [[sources/cursor--plugins-pstack#VE11]] [[sources/cursor--plugins-pstack#VE12]] [[sources/cursor--plugins-pstack#VE13]] [[sources/cursor--plugins-pstack#VE14]] [[sources/cursor--plugins-pstack#VE16]] [[sources/cursor--plugins-pstack#VE22]]
4. **Deadlock detection is deliberately disabled.** TLC receives `-deadlock` because quiescence is treated as normal rest. Liveness still requires the right explicit PROPERTY/fairness; a safety pass does not certify progress or deadlock freedom. [[sources/cursor--plugins-pstack#VE16]]
5. **Exit 0 is not “everything is correct,” and can accompany incomplete exploration.** Exact expected failures can return zero, including a valid found invariant counterexample followed by an error; the latter carries a warning. Downstream CI needs to distinguish baseline reproduction from absence-of-bugs evidence. [[sources/cursor--plugins-pstack#VE17]] [[sources/cursor--plugins-pstack#VE44]]
6. **Source links are heuristic reminders.** `uncitedConditions` scans certain conjuncts and accepts a citation regex. A direct local probe showed a nonexistent `nonexistent.ts:999999` suppresses the warning. The check runs in `--fixed`/`--against` modes, not every `from-spec` invocation, and does not establish semantic atomicity or entailment. [[sources/cursor--plugins-pstack#VE29]]
7. **Reader-state graphs are projections.** Same labels collapse model states, hidden steps can disappear, cause functions combine counterexamples, and comparison replays use shared state and words. The code reports mixed labels and divergences, but this is not general bisimulation checking. Region “proof” establishes equivalence to the flattened labeled projection under this parser's semantics. [[sources/cursor--plugins-pstack#VE19]] [[sources/cursor--plugins-pstack#VE20]] [[sources/cursor--plugins-pstack#VE21]] [[sources/cursor--plugins-pstack#VE22]] [[sources/cursor--plugins-pstack#VE23]] [[sources/cursor--plugins-pstack#VE24]] [[sources/cursor--plugins-pstack#VE25]] [[sources/cursor--plugins-pstack#VE26]]
8. **Annotation is not enforcement.** `timer()` and `guard()` labels are not checked against source or simulated wall time. A group cannot hide a violation's status, but that does not make an inaccurate state name truthful. [[sources/cursor--plugins-pstack#VE27]] [[sources/cursor--plugins-pstack#VE42]]
9. **The snapshot is selective and publication has boundaries.** Relative JS imports and neighboring TLA modules are recognized textually; computed imports, arbitrary filesystem/network data and other ambient inputs are outside this dependency capture. Comparison uses file content, not a globally atomic source-tree transaction. The map is copied but draw() imports and passes the original live mapping path; a transient mapping edit restored before content checks could escape that check. This is a source-derived limit, not a reproduced concurrency defect. The copy fallback explicitly permits mixed output under overlapping runs on non-renaming filesystems. [[sources/cursor--plugins-pstack#VE31]] [[sources/cursor--plugins-pstack#VE32]] [[sources/cursor--plugins-pstack#VE50]]
10. **Dependencies are installed by ordinary execution and test setup.** The CLI may download TLC/Java with mise and PNG dependencies with npm; the full test file invokes discovery/renderer loading at top level. This explains the isolated subset used here, not a claim that the suite has no integration tests. [[sources/cursor--plugins-pstack#VE33]] [[sources/cursor--plugins-pstack#VE39]]
11. **Parser boundary probes require cautious interpretation.** Direct `parseValue` probes collapse `9007199254740992` and `9007199254740993` through JS Number and preserve order for set-as-array keys (`{1,2}` differs from `{2,1}`). These demonstrate parser representations, not a reproduced defect in values emitted by pinned TLC 1.7.4; reachability of such outputs was not established. Do not present them as formal-checker bugs. [[sources/cursor--plugins-pstack#VE41]]
12. **Generated helpers and maintenance policies are instructions, not proven automation.** No generated application-specific verify skill was created or trialed in this investigation. The Notes examples are illustrative contracts, not a shipped Notes driver. Seed coverage of three to five features and proving one feature during generation are deliberately narrower than maintenance's every-feature requirement. ## Open questions / what's unclear

- How often do generated formal checks catch real implementation defects rather than defects in the authored model? No outcome study or effectiveness benchmark was run here. [[sources/cursor--plugins-pstack#VE07]] [[sources/cursor--plugins-pstack#VE14]]
- How much manual review is needed to keep coverage complete when writers of guarded state move across files or services? The maintenance skill requires discovery but supplies no universal dependency analyzer. [[sources/cursor--plugins-pstack#VE11]]
- Which supported runtimes exhibit the piped-help truncation, and should CLI exits drain output explicitly? Only the observed local Node version is established. [[sources/cursor--plugins-pstack#VE38]] [[sources/cursor--plugins-pstack#verification-local-checks]]
- Should interrupted runs terminate child TLC processes, and should non-atomic publication fallback be rejected for shared output directories? These are proposed extensions, not existing guarantees. [[sources/cursor--plugins-pstack#VE32]] [[sources/cursor--plugins-pstack#VE43]]
- When does a reader projection become too coarse to explain a bug? The tool detects several ambiguity cases, but choosing sufficient labels remains a modeling responsibility. [[sources/cursor--plugins-pstack#VE20]] [[sources/cursor--plugins-pstack#VE21]] [[sources/cursor--plugins-pstack#VE22]]
