# pstack

> An opinionated engineering toolkit that turns a task into bounded investigation, explicit decisions, parallel execution, and inspectable verification—with reusable rules for improving the toolkit itself.

**Research judgment:** its most valuable contribution is the connection between *how to think* and *what must exist afterward*: a discriminating experiment, a reusable script, a source-backed answer, a reviewed revision, or a verification model maintained alongside the implementation. The principles are useful independently; the workflow coordinates them; the scripts give a subset executable teeth. These are different evidence classes, not interchangeable guarantees. ## What problem it solves

A capable coding model can still pursue the wrong premise, mistake activity for evidence, serialize work unnecessarily, or repeat a lesson without changing its future behavior. Pstack supplies reusable interventions at these failure points. Its organizing idea is that parallel work becomes useful only after each unit can produce a result another agent or human can inspect. The 24 principles name judgment moves; playbooks sequence them; verification and orchestration tools preserve state and expose failures. [[sources/cursor--plugins-pstack#PK02]] [[sources/cursor--plugins-pstack#PK20]] [[artifacts/skills/poteto-mode]]

## Composition strategy

**Canonical text → selected playbook → bounded workers → observable checks → durable improvement.** `poteto-mode` is the main route, while setup keeps model policy in a separate user configuration. Formal-verification skills generate project-local verification assets that must be maintained as code changes. `reflect` and `correct` operate at different levels: a workflow lesson may become a skill, while a repeated code defect should become an architectural/type/lint/test constraint. [[sources/cursor--plugins-pstack#PK10]] [[sources/cursor--plugins-pstack#PK18]] [[artifacts/skills/poteto-mode]] [[artifacts/skills/statechart]]

Cross-harness packaging is generated from canonical content. At this revision 23 skill files receive a Claude Code adapter reference; other skills copy directly. The adapter maps capabilities and discloses unavailable features. This avoids hand-maintained forks, but mapping cloud execution to a worktree or an unavailable model to the session model changes the guarantee. Treat portability as a declared set of semantic compromises, not merely a folder-format conversion. [[sources/cursor--plugins-pstack#PK04]] [[sources/cursor--plugins-pstack#PK05]] [[sources/cursor--plugins-pstack#PK07]]

## What makes it great

1. **It describes decisions in terms of observable consequences.** A principle must change an actual decision; a lever must be a runnable artifact; a performance claim must explain its limiter. [[sources/cursor--plugins-pstack#PK20]] [[sources/cursor--plugins-pstack#PP03]] [[sources/cursor--plugins-pstack#PP07]]
2. **It separates engineering layers that agents often blur.** Domain invariants, workflow gates, model fidelity, review freshness, and user communication have distinct owners. [[sources/cursor--plugins-pstack#PP15]] [[artifacts/skills/poteto-mode]] [[artifacts/skills/statechart]]
3. **It makes self-improvement concrete.** Historical failures become constraints or reusable workflows; the proposal must name the failure class and where future behavior changes. [[sources/cursor--plugins-pstack#PK18]] [[sources/cursor--plugins-pstack#PP04]]
4. **It includes substantial executable machinery.** This is not only a prompt collection. That makes it more inspectable, while also introducing ordinary software bugs and lifecycle obligations. See the executed-check record and limitations below. [[sources/cursor--plugins-pstack#local-checks]]

### Engineering judgment and work structure

- **P01 ★ Make repeated work leave a runnable lever.** Do one representative unit correctly, compare automated output to that oracle, then reuse an idempotent script/codemod. Parallel workers share the recipe; they do not improvise it independently. [[sources/cursor--plugins-pstack#PP03]]
- **P02 ★ Encode lessons at the strongest practical layer.** Prefer architecture, types, actionable lint/CI, or behavioral tests; reserve prose for irreducible judgment. Remove a redundant instruction once structure makes its violation impossible. [[sources/cursor--plugins-pstack#PP04]] [[sources/cursor--plugins-pstack#PK18]]
- **P03 Name the decision a principle changed.** A short steering label is useful when it selects a different action, not when it is merely echoed in a rationale. [[sources/cursor--plugins-pstack#PK20]]
- **P04 ★ Attack a shared premise after repeated failure.** If two attempts depend on the same assumption, design an observation that could invalidate it before trying a third variation. [[sources/cursor--plugins-pstack#PP01]]
- **P05 Explore alternatives before polishing one.** Map materially different designs and compare them against real constraints; a small edit to the first idea does not establish that it wins. [[sources/cursor--plugins-pstack#PP05]]
- **P06 Work backward from the actual user experience.** Make success tangible, then select implementation steps that produce that experience. A component's existence is weaker evidence than the promised behavior working. [[sources/cursor--plugins-pstack#PP06]]
- **P07 ★ Explain measured results before trusting them.** Find the limiter in a profile or system counters taken during the run, rule out skipped/cached work and other confounds, and retain run count and spread. Ask why the result is not twice as good; a code-reading guess is not an observed limiter. [[sources/cursor--plugins-pstack#PP07]]
- **P08 Fix the producing mechanism, not just the visible instance.** Trace causality and check the correction covers equivalent cases without silently expanding scope. [[sources/cursor--plugins-pstack#PP08]]
- **P09 Derive the foundation before choosing a framework.** Enumerate domain requirements, state ownership, and invariants; let storage and decomposition follow those facts. [[sources/cursor--plugins-pstack#PP09]] [[sources/cursor--plugins-pstack#PP15]]
- **P10 Budget context as working capacity.** Keep authoritative facts in artifacts, delegate bounded reads, and return distilled evidence instead of filling the main context with raw exploration. [[sources/cursor--plugins-pstack#PP10]]
- **P11 Delete unnecessary work before optimizing it.** Reduce the actual obligation, but preserve the outcome that made it necessary. [[sources/cursor--plugins-pstack#PP11]] [[sources/cursor--plugins-pstack#PP22]]
- **P12 ★ Reconcile from observed state.** Design retries to converge and interruption points to be recoverable; a retry loop alone does not establish idempotence or exactly-once effects. [[sources/cursor--plugins-pstack#PP12]]
- **P13 Complete internal API migrations.** Update callers and remove the obsolete path; preserve compatibility only where real external consumers or migration constraints require it. [[sources/cursor--plugins-pstack#PP13]]
- **P14 Reduce both reader indirection and mutable context.** A smaller file can still be harder to understand if its meaning depends on scattered decisions or hidden state. [[sources/cursor--plugins-pstack#PP14]]
- **P15 Put each invariant under an explicit owner.** Group code by meaning and valid state, not only by chronological processing phase. [[sources/cursor--plugins-pstack#PP15]]
- **P16 Continue independent work while a human decision is pending.** Surface a concrete choice and its cost; do not turn missing preference into invented authorization. This last boundary is our adaptation of an aggressive autonomy principle. [[sources/cursor--plugins-pstack#PP16]]
- **P17 Define the endpoint before counting activity.** Keep the full authorized goal distinct from temporary scaffolding or intermediate milestones. [[sources/cursor--plugins-pstack#PP17]]
- **P18 ★ Require evidence capable of disproving success.** Show actual output at the claimed boundary; code inspection and proxy checks should not silently become user-flow proof. [[sources/cursor--plugins-pstack#PP18]]
- **P19 Redesign around current constraints.** Historical organization is evidence to understand, not an obligation to preserve after its reason disappears. [[sources/cursor--plugins-pstack#PP19]]
- **P20 ★ Separate independent state before adding locks.** Give actors separate writable artifacts where possible, merge at a deliberate boundary, and serialize only genuinely shared canonical state. [[sources/cursor--plugins-pstack#PP20]]
- **P21 Sequence units that can be verified.** Preserve the larger destination while giving each integration unit an observable contract; explicitly scoped temporary breakage needs a recovery path. [[sources/cursor--plugins-pstack#PP21]]
- **P22 Test two counterfactuals.** The check should fail when behavior breaks and survive a harmless implementation refactor. [[sources/cursor--plugins-pstack#PP23]]
- **P23 Parse uncertain inputs at boundaries.** Let validated domain types carry established facts internally; this depends on the boundary and mutation model actually preserving them. [[sources/cursor--plugins-pstack#PP02]] [[sources/cursor--plugins-pstack#PP24]]
- **P24 Strengthen types only where operations are partial or confusion is real.** Use tagged states, derived data, and non-empty/brand distinctions to remove actual lies; do not decorate every value automatically. [[sources/cursor--plugins-pstack#PK11]]
- **P25 Test the alleged impossible state.** A nicer representation is not an invariant proof: plain numeric duration still admits negative values. Constructors, guards, and meaningful negative fixtures must carry the promised restriction. [[sources/cursor--plugins-pstack#PK12]] [[sources/cursor--plugins-pstack#type-negative-probe]]

- **P26 Make one-off work rerunnable when that is how a reviewer can check it.** The source applies build-the-lever to nontrivial analysis and verification too; repetition is sufficient but not required. Build the smallest artifact that proves the job, not a framework. [[sources/cursor--plugins-pstack#PP03]]

### Compounding and output quality

- **P27 Turn recurrence into a defect class.** `correct` looks for repeated failures, builds enforcement, and uses historical negatives rather than only the fixed example. [[sources/cursor--plugins-pstack#PK18]]
- **P28 Use the same check locally and in CI.** An actionable diagnostic and predictable exception path matter more than adding another prose rule. [[sources/cursor--plugins-pstack#PK18]]
- **P29 Ratchet legacy violations without blessing new ones.** Baseline existing debt; keep exceptions justified, expiring, and human-approved rather than suppressing an entire rule. [[sources/cursor--plugins-pstack#PK18]]
- **P30 Maintain a rule-to-enforcer map.** Know which rules are architectural, typed, linted, tested, or still judgment-only; remove dead or redundant policy. [[sources/cursor--plugins-pstack#PK18]]
- **P31 Sharpen the missing professional work.** Improve a task along expertise, raw inputs, methods, and external checks while preserving the user's decisions. Better wording should not change the business objective. [[sources/cursor--plugins-pstack#PK17]]
- **P32 Replace explanatory comments with a better representation when it actually preserves meaning.** Keep external rationale and constraints if no equivalent structural home exists; the source's aggressive deletion branch is a caution, not a universal recipe. [[sources/cursor--plugins-pstack#PK15]]
- **P33 Classify a document's job first.** Tutorial, task guide, reference, and explanation need different sequencing and density. [[sources/cursor--plugins-pstack#PK13]]
- **P34 Use consistent domain words and causal sentences.** Name what changes, why, and what the reader can do next; concision should not remove the grammar needed to understand it. [[sources/cursor--plugins-pstack#PK13]]
- **P35 Keep editorial rules addressable and conditional.** Stable IDs make feedback precise; semantic review and preserving clarity matter more than mechanically banning a word or punctuation mark. [[sources/cursor--plugins-pstack#PK14]]
- **P36 Repair a conversational miss once.** Acknowledge the concrete error and supply the correction; repeated apologies add another burden. [[sources/cursor--plugins-pstack#PK19]]

### Configuration, distribution, and interfaces

- **P37 ★ Configure roles against discovered capabilities.** Model names and tool availability come from the current host/session, not remembered marketing labels. [[sources/cursor--plugins-pstack#PK10]]
- **P38 Separate role policy from workflow content.** User preferences survive skill updates when setup writes a dedicated configuration; reruns should update that file idempotently and retire obsolete roles. [[sources/cursor--plugins-pstack#PK10]]
- **P39 Make fallback constraints explicit.** Same-family fallback and effort limits are a policy, not a claim that a cheaper/unavailable model is interchangeable. A reasoning budget is not a dollar cap. [[sources/cursor--plugins-pstack#PK10]]
- **P40 Count actual independent reviewers.** Multiple aliases or personas that resolve to one model may offer different lenses but do not establish cross-model independence. [[sources/cursor--plugins-pstack#PK10]] [[sources/cursor--plugins-pstack#PK07]]
- **P41 ★ Generate platform copies from one canonical tree.** Validate names/frontmatter and manifest parity, add adapters only where needed, and fail on content or executable-bit drift. [[sources/cursor--plugins-pstack#PK04]] [[sources/cursor--plugins-pstack#PK06]] [[sources/cursor--plugins-pstack#PK23]]
- **P42 Document capability loss at the adaptation point.** A worktree is not a cloud runner; a replacement context is not a resumed session; an instruction to remain read-only is not a sandbox. [[sources/cursor--plugins-pstack#PK07]]
- **P43 Prefer version-pinned external references in generated packages.** Source links rewritten to `main` can drift beyond the installed version; this is our improvement to the observed generator. [[sources/cursor--plugins-pstack#PK05]]
- **P44 Derive documentation inventory from the tree.** Count commands/principles/playbooks, distinguish full counts from subsets, and validate referenced names against the canonical configuration. [[sources/cursor--plugins-pstack#PK08]]
- **P45 Give each checker an explicit coverage boundary.** Packaging parity and guide-link checks can both pass while a skill-local link is broken. Add a negative fixture for the promised class before treating a checker as comprehensive. [[sources/cursor--plugins-pstack#packaging-negative-probe]]
- **P46 Keep interface credentials on the server.** Accept a deliberately small payload, validate it as untrusted input, and let the server compose the wake request. [[sources/cursor--plugins-pstack#PK16]]
- **P47 Verify a wake with a harmless real request.** Bounded timeout and failure logging make failure visible; they do not establish delivery, deduplication, or durable acknowledgement. [[sources/cursor--plugins-pstack#PK16]]
- **P48 Treat network exposure as a separate contract.** A snippet bound to `0.0.0.0` over HTTP needs deployment-specific access control; a private-network suggestion is not itself a route authentication check. [[sources/cursor--plugins-pstack#PK16]]

### Research, review, learning, and automation ledger

The following mechanisms are predominantly **prompt policies**, including the agents, review loops, and Benny workflows. The inspected shell log helper is labeled separately. These instructions were studied as source; no model-quality, deployed automation, or provider-compatibility result is claimed. ★ marks the strongest portable ideas.

### Reasoning and investigation

- **RE01 — ★ Separate mechanism, motivation, consequence, and teaching.** *Prompt policy.* `how` owns runtime behavior and placement; `why` owns the forces behind historical choices; blast-radius examines downstream breakage; teach composes mechanics and rationale for a reader. This is a useful inquiry API: choose the question before choosing evidence. Reuse these distinct contracts instead of asking one generic researcher to explain everything. Code can establish mechanism without establishing author intent, and a convincing explanation cannot substitute for a safety experiment. [[sources/cursor--plugins-pstack#RE01]]

- **RE02 — Proportional exploration rather than mandatory fan-out.** *Prompt policy.* How uses one explainer for a narrow module question, two to four distinct explorers for a subsystem, and defaults to the simpler route when uncertain. Ambiguity becomes a stated working interpretation that the user can redirect. Reuse this as a cost-control rule: parallelism should buy distinct coverage. It is a heuristic, not a measured optimum; Why deliberately takes the opposite, coverage-heavy default, so callers need an explicit scope contract. [[sources/cursor--plugins-pstack#RE02]]

- **RE03 — Exploration returns a traceable intermediate representation.** *Prompt policy.* Each explorer returns components, step-by-step control/data flow, every file read, subsystem inputs/outputs, surprising behavior, and open questions. A separate explainer reconciles overlaps and checks contradictory findings against code instead of simply concatenating summaries. Reuse this evidence handoff for parallel repository work: it makes missing boundaries visible and preserves paths for audit. The file list records inspection, not comprehension; synthesis still depends on the model recognizing a contradiction. [[sources/cursor--plugins-pstack#RE03]]

- **RE04 — Explanations optimize for a working mental model.** *Prompt policy.* How separates overview, key concepts, execution flow, a minimal file map, and optional gotchas; concrete calls replace abstractions-about-abstractions. Diagrams appear only when relationships need them. Reuse this shape for onboarding and ownership questions, where the reader needs enough structure to act rather than a source-code recital. Optional sections avoid ritual padding. This output template is a communication policy, not a test that a reader can successfully modify the subsystem. [[sources/cursor--plugins-pstack#RE04]]

- **RE05 — ★ Historical research starts from a code anchor.** *Prompt policy.* Why builds shared seed context from exact lines, symbols, blame, history through renames, merge-PR numbers, complete PR bodies/reviews, and linked tickets. Its archaeology playbook adds pickaxe searches, co-change, ADRs, TODOs, and tests. Reuse this to tie broad research to the actual decision under investigation and prevent recency bias. Commit history records what survived review; squash merges, missing discussions, deleted branches, and inaccurate author narratives limit causal completeness. [[sources/cursor--plugins-pstack#RE05]]

- **RE06 — ★ Coverage is an explicit artifact, including nulls.** *Prompt policy.* Why discovers available integrations and maps them to seven evidence categories: source control, tickets, long-form docs, chat, infrastructure, errors, and analytics. Unavailable sources and justified skips appear in the final coverage map; empty queries are findings rather than omitted work. Reuse a coverage ledger to distinguish searched-and-empty from inaccessible or irrelevant. One chosen tool per category does not establish exhaustive coverage of every available source, and the default full sweep can be disproportionate. [[sources/cursor--plugins-pstack#RE06]]

- **RE07 — Partition evidence gathering by source, not final conclusion.** *Prompt policy.* Investigators own one source, read complete items, follow only same-source links, and return cross-source references as leads. They gather evidence, alternatives, contradictions, and verbatim queries rather than decide the final story. A synthesizer merges duplicate references and reasons across sources. Reuse this to reduce duplicated retrieval and premature narrative convergence. A second pass must actually route those leads, or source ownership can become a boundary that strands important evidence. [[sources/cursor--plugins-pstack#RE07]]

- **RE08 — ★ Claim-level epistemic types survive presentation.** *Prompt policy.* Why assigns each claim Direct, Supported, Inferred, Speculative, or Unknown; adjacent citations and phrasing must match the tier. The parent may edit clarity but may not rewrite confidence language, and Teach inherits that constraint. Reuse confidence as part of the evidence payload, not removable prose style. Direct means someone explicitly wrote the rationale, not that the statement is objectively correct; converging indirect items can share one underlying source and should not be counted as independent confirmation. [[sources/cursor--plugins-pstack#RE08]]

- **RE09 — ★ Resist retrospective rationalization and user-supplied hypotheses.** *Prompt policy.* Why forbids inferring intent from behavior, retrofitting a tidy rationale, turning missing evidence into absence, and rubber-stamping the user’s suggested explanation. Investigators ask whether the same evidence would appear if their interpretation were wrong; synthesis preserves competing hypotheses and evidence against each. Reuse this as a falsification check in incident research and design archaeology. The rules reduce a known failure mode but do not guarantee calibrated probabilities or independence from the question’s framing. [[sources/cursor--plugins-pstack#RE09]]

- **RE10 — Historical artifacts need lifecycle and scope checks.** *Prompt playbooks.* Ticket research follows parents, comments, duplicate chains, milestones, and changed scope. Document research checks full content, draft/final status, dates, alternatives, and divergence from shipped code. Chat research fetches full threads, bounds by author/PR/date, and separates jokes from decisions. Reuse artifact lifecycle metadata alongside the quote itself. None of these sources is authoritative merely because it has a “Why” heading; boilerplate, stale drafts, restricted pages, and missing DMs remain explicit gaps. [[sources/cursor--plugins-pstack#RE10]]

- **RE11 — Runtime and product evidence answer different questions.** *Prompt playbooks.* Datadog’s playbook starts with owning services, dashboards, monitors, bounded metrics/logs, spans, and incidents. Databricks asks about user events, experiments, billing, query cost, and data lineage. Sentry follows first/last-seen, releases, breadcrumbs, and representative traces. Defensive code adds incident-shaped queries across existing sources. Reuse this evidence taxonomy to avoid asking infrastructure telemetry to answer product motivation. Tool names and schema examples are environment-specific, and telemetry association does not itself prove why code was written. [[sources/cursor--plugins-pstack#RE11]]

- **RE12 — ★ Retention gaps and instrumentation changes are not negative evidence.** *Prompt playbooks.* Telemetry playbooks distinguish no events from inaccessible/expired history, flag instrumented-versus-caused reasoning, and warn that a chart’s framing can mislead. Analytics adds schema drift, refresh lag, duplicate raw events, and logging changes that mimic a feature launch. Reuse these as mandatory caveats when comparing before/after charts. A temporal match can guide a hypothesis; attribution requires contemporaneous decision evidence or stronger experimental isolation. [[sources/cursor--plugins-pstack#RE12]]

- **RE13 — Bound and orient analytical queries before interpreting them.** *Prompt playbook.* The warehouse guide probes tables and columns, time-bounds every query around the change, prefers typed/deduplicated models, polls asynchronous statement IDs rather than rerunning, and returns exact SQL plus compact counts/percentiles instead of raw rows. Reuse this as a resource and reproducibility contract for analytics-backed investigation. Its standard-column conventions and ±30-day example remain organization-specific assumptions; querying them correctly does not make a selected percentile the real source of a threshold. [[sources/cursor--plugins-pstack#RE13]]

- **RE14 — Machine-generated diagnoses are leads; preserve source authority.** *Prompt policy.* Sentry’s AI root-cause tool is explicitly a hypothesis generator; events and stack traces remain primary evidence. Why’s synthesizer spot-checks uncertain citations and turns lineage into Preserve / Change / Avoid / Risk constraints when the question precedes an edit. Reuse this to translate research into decisions without laundering a model answer into a fact. Spot checks leave unverified citations, and a historical constraint may need fresh validation before it should bind a new design. [[sources/cursor--plugins-pstack#RE14]]

- **RE15 — Read-only intent and tool permissions can diverge.** *Prompt policy; limitation.* Why and Reflect request agent mode with readonly=false because their stated Cursor environment removes MCP access in read-only mode, then forbid investigators from writing in prose. This exposes a portable design requirement: read capability and write authority should be separately expressible. Reuse the research contract, but implement real capability scoping when available. The instructions do not demonstrate that write tools are removed, and the claimed platform behavior was not tested here. [[sources/cursor--plugins-pstack#RE15]]

- **RE16 — ★ Consumer usage is the design specification.** *Prompt policy.* Architect asks for README-style usage and realistic call sites before types, signatures, and module maps. When they diverge, the sketch changes to fit the caller, not vice versa. Rationale records hidden complexity, public surface, invariants, validation boundaries, accepted tradeoffs, rejected alternatives, and next step. Reuse this to discover a difficult API before implementation entrenches it. A handpicked usage example can omit awkward real consumers; grounded access patterns must still test the proposed shape. [[sources/cursor--plugins-pstack#RE16]]

- **RE17 — Ground ownership changes in mechanism and history.** *Prompt policy.* Architect invokes How over affected systems and Why when ownership or layering changes; only genuinely greenfield work skips this. Human pushback becomes new grounding evidence before another sketch, rather than a patch to defend the first proposal. Reuse the Preserve/Change/Avoid/Risk output to give design search concrete constraints. This is a strong dependency on the research workflows, and broad historical retrieval can dominate the cost of a small change. [[sources/cursor--plugins-pstack#RE17]]

- **RE18 — Design twice, with truly different shapes.** *Prompt policy.* Architect requires at least two structurally distinct candidates before synthesis. Independent runners receive shared grounding and isolated worktrees or directories, then argue for their strongest design instead of a safe compromise. Reuse alternatives as a way to expose the cost of a first attractive shape. Different model families and folders are not proof of independent assumptions; multiple prompts may still converge because the task supplied the same hidden bias. [[sources/cursor--plugins-pstack#RE18]]

- **RE19 — ★ Design for locally informed future agents.** *Prompt policy.* Architect assumes a future contributor sees only opened files, copies nearby examples, and chooses the shortest compiling path. ### Review and verification

- **RE25 — Review execution against stated intent, without auto-apply.** *Prompt policy.* Interrogate first packages the full relevant changeset and states intent, then gives every model the same adversarial rubric. It explicitly derives diversity from models rather than assigned personas and returns a verdict without applying edits. Reuse this when the goal is already settled and implementation needs pressure. The reviewer is instructed not to question intent, so this is not a product-validity or ethical-goal review; upstream scope errors can survive a technically excellent review. [[sources/cursor--plugins-pstack#RE25]]

- **RE26 — ★ Real execution paths beat hypothetical review findings.** *Prompt policy.* Reviewers must identify concrete locations, severity, evidence, and optional alternatives; “no findings” is valid. The lead traces whether nulls or other feared inputs can actually reach the code, rejects preference masquerading as defects, and recognizes nitpick gravity. Reuse a finding contract that demands a reachable failure mechanism. These checks still need enough surrounding context; a diff-only review can miss preconditions, and apparent consensus does not repair missing evidence. [[sources/cursor--plugins-pstack#RE26]]

- **RE27 — A lead reviewer makes judgments instead of counting votes.** *Prompt policy.* Interrogate deduplicates findings, retains which models raised them and explicit disagreements, then classifies Act on, Consider, Noted, or Dismissed with reasons. The lead gives extra scrutiny to singleton correctness/security concerns even while treating independent agreement as signal. Reuse this to keep minority discoveries and rejected findings auditable. No statistical model supports the confidence weighting, and “two models agreed” can reflect the same training or prompt bias. [[sources/cursor--plugins-pstack#RE27]]

- **RE28 — Review covers contracts outside the diff.** *Prompt rubric.* The rubric checks crash/retry idempotency, structural concurrency ownership, canonical boundaries, actual data access patterns, obsolete compatibility paths, real output artifacts, and user value relative to complexity. It specifically distinguishes a live measurement from proxy liveness and an artifact from a delegated worker’s self-report. Reuse these lenses to challenge code that passes superficial local tests. They are review prompts, not guarantees that all reachable paths or integrations were exercised. [[sources/cursor--plugins-pstack#RE28]]

- **RE29 — Keep review heuristics subordinate to concrete costs.** *Prompt policy; internal tension.* The code-quality lens pushes structural simplification and treats crossing 1,000 lines, wrappers, cast-heavy contracts, or missed “code judo” as presumptive blockers. Yet the lead framework rejects speculative abstraction and the rubric says simple code need not have an abstraction. Reuse the demand to justify complexity, not the threshold as a universal gate. A review lead needs an explicit override rationale when the aggressive lens conflicts with the smaller, clearer design. [[sources/cursor--plugins-pstack#RE29]]

- **RE47 — ★ Review the load-bearing safety fact with executable evidence.** *Prompt policy.* Blast-radius asks for the one or two facts on which safety depends, then escalates from assertion to source citation, failure-path reasoning, execution against real code, and reproduction in the running app. The final report names the achieved level or says unproven. Reuse this to focus review effort on a falsifiable safety lemma. A single fact is an optimization heuristic, not a proof that every regression risk is covered; “ran it” still needs representative inputs and the correct revision. [[sources/cursor--plugins-pstack#RE47]]

- **RE48 — Trace impact beyond what a symbol search can find.** *Prompt policy.* Blast-radius follows pinned dependency source and local patches, scheduling/lifecycle behavior, JSON and database contracts, wire bytes read by another language, flags, and downstream consumers. It separates confirmed risks from cleared ones, with likelihood, impact, and a cheap discriminating test. Reuse this for deceptively small diffs. The skill asks for a “real chance” but supplies no probability estimator; ordinal or explicitly uncertain judgments are safer than invented numerical precision. [[sources/cursor--plugins-pstack#RE48]]

- **RE49 — ★ When no playbook fits, design a falsifiable workflow first.** *Prompt policy.* Figure-it-out defines done as a predicate, quantifies scope, scales gates/artifacts to reversibility and blast radius, sequences the riskiest unknown first, and captures a pre-change baseline before implementation. It uses architecture exploration for one-way design choices but avoids repeating an arena over settled mechanics. Reuse this as workflow synthesis, not an invitation to free-form autonomy. Baselines and predicates can encode the wrong objective; both need scrutiny before a long run consumes its budget. [[sources/cursor--plugins-pstack#RE49]]

- **RE50 — Experiments verify units and repair the gate separately.** *Prompt policy.* Each figure-it-out unit states a hypothesis, makes the smallest change, measures the real artifact, retains progress or reverts, and verifies before continuing. Delegated work gets a judge; an easily passed check triggers suspicion about observation. Worker gaming hardens the contract, while a wrong gate changes in its own change. Reuse VERIFIED / NOT VERIFIED / INCONCLUSIVE as distinct states. The prompt does not mechanically enforce isolation, reversion, or a correct judge, and “inconclusive” must never become success by timeout. [[sources/cursor--plugins-pstack#RE50]]

A rejection window is a coordination courtesy inside a previously configured workflow, not general approval by silence; eliminating all competing hypotheses may be infeasible. [[sources/cursor--plugins-pstack#RE76]]

- **RE77 — Fix delivery is gated by real after evidence and nearby behavior.** *Prompt policy.* The patched UI repeats the same path twice, captures after media and the same state cross-check, then runs focused tests and a blast-radius smoke across nearby states, inputs, permissions, platforms, and failures. Only then may it open a draft PR with evidence, root cause, tests, and tracker link; it never merges or deploys. Reuse the distinction between compiling, passing a proxy, and resolving the reported behavior. Evidence checks and draft-only delivery are prescribed, not runtime-enforced. [[sources/cursor--plugins-pstack#RE77]]

- **RE78 — Cleanup and capability readiness are part of the contract.** *Prompt policy.* The adapter reports supported feature sections before work, bounds retries, keeps secrets/captures out of source, and removes only processes, profiles, fixtures, tunnels, and expired artifacts it owns. Setup exercises a harmless full startup/navigation/state/capture/recording/cleanup path before enabling repro. Reuse resource ownership and evidence retention as lifecycle concerns, not a final vague “clean up.” No janitor or retention scheduler is implemented here; a crashed run can leave artifacts unless the host supplies recovery.
