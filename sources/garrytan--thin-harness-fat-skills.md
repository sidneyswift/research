# "Thin Harness, Fat Skills" (`garrytan`, essay #1 of 8)

> The opening essay of Garry Tan's 8-part "AI Explainer" series and the **architectural thesis statement** for the whole sequence: the gap between a "2x" and a "100x" AI engineer "isn't intelligence — it's architecture, and it fits on an index card." Introduces the series' five primitives (skill files, the thin harness, resolvers, the latent-vs-deterministic split, diarization), the three-layer architecture (fat skills → thin ~200-line CLI → deterministic app), and the "codify everything / never do one-off work" discipline. Our primary source for the *named* `thin-harness-fat-skills` pattern, the `skill-as-method-call` and `diarization` framings, and the earliest star/usage figures in the longitudinal series.

## Anchor map

Every claim citing this source uses a `#anchor` from this list. The essay is one prose file; anchors are thematic pointers into the author's own section headers and named claims. **Do not invent anchors beyond this list** — register new ones here first.

- `#root` — the essay as a whole
- `#index-card-thesis` — the framing claim: 2x vs 100x engineers run *the same models*; "the difference isn't intelligence. It's architecture — and it fits on an index card." Opens with the Steve Yegge "10x to 100x… roughly 1000x as productive as Googlers in 2005" quote.
- `#harness-is-the-product` — "the secret isn't the model, it's the thing wrapping the model"; the Anthropic Claude Code npm source leak ("March 31, 2026… 512,000 lines. I read it"); the harness = live repo context + prompt caching + purpose-built tools + context-bloat minimization + structured session memory + parallel sub-agents.
- `#five-definitions` — framing for the five primitives: "the bottleneck is never the model's intelligence… they fail because they don't understand *your* data."
- `#skill-files` — Definition 1. A skill file is reusable markdown that teaches the model *how*, not *what*; "software design, using markdown as the programming language and human judgment as the runtime."
- `#skill-as-method-call` — the core claim inside Definition 1: a skill file "works like a method call… takes parameters." The `/investigate` example with TARGET / QUESTION / DATASET → safety scientist + 2.1M discovery emails vs. shell company + FEC filings. "Same skill. Same seven steps." Grounds [[patterns/behavioral/skill-as-method-call]].
- `#the-harness` — Definition 2. The harness does four things: run the model in a loop, read/write files, manage context, enforce safety — "that's the thin." The fat-harness anti-pattern (40+ tool defs, god-tools, REST-wrapper-per-endpoint, "3× tokens, 3× latency, 3× failure rate").
- `#playwright-cli-75x` — the purpose-built-tooling sub-claim: a Playwright CLI at ~100 ms/op vs. a Chrome MCP at ~15 s for screenshot-find-click-wait-read = "75x faster." "Software doesn't have to be precious anymore."
- `#resolvers` — Definition 3. A resolver is "a routing table for context… when task type X appears, load document Y first." Skills tell the model *how*; resolvers tell it *what* to load and *when*. The `docs/EVALS.md` example (loads "if accuracy drops >2%, revert"). Grounds [[patterns/composition/resolver-routing-table]].
- `#description-is-the-resolver` — sub-claim of Definition 3: "Claude Code has a built-in resolver. Every skill has a description field, and the model matches user intent to skill descriptions automatically… The description *is* the resolver."
- `#twenty-thousand-line-claude-md` — the confession: "my CLAUDE.md was 20,000 lines… the model's attention degraded. Claude Code literally told me to cut it back. The fix was about 200 lines — just pointers to documents." (author self-anecdote; the resolver-as-thin-index claim.)
- `#latent-vs-deterministic` — Definition 4. Every step is latent (model judgment: read/interpret/decide/synthesize) or deterministic (same input → same output: SQL, compiled code, arithmetic). "Confusing them is the most common mistake in agent design." The 8-vs-800 dinner-seating example (combinatorial optimization forced into latent space hallucinates). Grounds [[patterns/behavioral/latent-vs-deterministic-split]].
- `#diarization` — Definition 5. "The model reads everything about a subject and writes a structured profile — a single page of judgment distilled from dozens or hundreds of documents… the difference between a database lookup and an analyst's brief." "No SQL query produces this. No RAG pipeline produces this." Grounds [[patterns/behavioral/diarization]].
- `#three-layer-architecture` — "The architecture": fat skills on top (90% of the value), a thin CLI harness in the middle ("about 200 lines… JSON in, text out. Read-only by default"), the application on the bottom (QueryDB, ReadDoc, Search, Timeline). "Push intelligence up. Push execution down. Keep the harness thin." Grounds [[patterns/structural/thin-harness-fat-skills]].
- `#system-that-learns` — the worked end-to-end example: "an actual system we're building at YC" for Startup School (Chase Center, July 2026, 6,000 founders). The 15-person program team that "works at 200 founders, breaks at 6,000."
- `#enrich-founder` — the `/enrich-founder` skill (pulls all sources, enriches, diarizes, "highlights the gap between what founders *say* and what they're *actually building*"). The Maria Santos / Contrail example ("SAYS: 'Datadog for AI agents' / ACTUALLY BUILDING: 80% of commits in billing module → a FinOps tool disguised as observability"). The deterministic layer = SQL lookups, GitHub stats, browser tests on demo URLs, social pulls, CrustData queries; "a cron runs nightly… 6,000 profiles, always fresh."
- `#match-skills` — the three matching invocations of one skill: `/match-breakout` (1,200 founders, cluster by sector, 30/room, embedding + deterministic assignment), `/match-lunch` (600, serendipity across sectors, 8/table, no repeats — "the LLM invents the themes, then a deterministic algorithm assigns seats"), `/match-live` (whoever's in the building, nearest-neighbor embedding, 200 ms, 1:1, exclude already-met). The Santos/Oram "not competitors" and Kim "developer tools → SOC2 compliance → move to FinTech/RegTech" judgment calls. "No embedding captures the Kim reclassification."
- `#learning-loop` — the `/improve` skill: reads NPS surveys, diarizes the *mediocre* ("OK") responses, extracts patterns, "proposes new rules and writes them back into the matching skills… The skill rewrites itself." "July event: 12% 'OK'. Next event: 4%." Grounds the self-modifying side of [[patterns/quality-bar/complexity-ratchet]].
- `#codify-everything` — the OpenClaw instruction: "You are not allowed to do one-off work… do it manually the first time on 3 to 10 items… If I approve, codify it into a skill file. If it should run automatically, put it on a cron. The test: if I have to ask you for something twice, you failed." Reported as "a thousand likes and twenty-five hundred bookmarks."
- `#permanent-upgrades` — the close: "Every skill you write is a permanent upgrade… It never degrades… runs at 3 AM while you sleep. And when the next model drops, every skill instantly gets better — the judgment in the latent steps improves while the deterministic steps stay perfectly reliable… That's how you get Yegge's 100x… The system compounds. Build it once. It runs forever."

## Why we cite this

- **The canonical, first-person statement of the `thin-harness-fat-skills` architecture** — this essay *is* the namesake of [[patterns/structural/thin-harness-fat-skills]]. It gives the exact shape (fat skills on top = 90% of value / ~200-line CLI / read-only-by-default / JSON-in-text-out / deterministic app at the bottom) and the directional rule ("push intelligence up, push execution down"). ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]])
- **The clearest articulation of `skill-as-method-call`** in the series — a skill file is a parameterized markdown procedure (TARGET / QUESTION / DATASET); same file, different invocation → different capability. The `/investigate` and `/match-*` examples are the grounding narrative. ([[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]], [[sources/garrytan--thin-harness-fat-skills#match-skills]]) Grounds [[patterns/behavioral/skill-as-method-call]].
- **The `latent-vs-deterministic` split as a *design discipline*** — "every step is one or the other; confusing them is the most common mistake." The 8-vs-800 seating example is the quotable counter-case. ([[sources/garrytan--thin-harness-fat-skills#latent-vs-deterministic]]) Grounds [[patterns/behavioral/latent-vs-deterministic-split]].
- **The `diarization` primitive** — read everything about a subject, write one page of distilled judgment; the "says vs. actually building" gap. ([[sources/garrytan--thin-harness-fat-skills#diarization]], [[sources/garrytan--thin-harness-fat-skills#enrich-founder]]) Grounds [[patterns/behavioral/diarization]] — and it is grounded *in the real repo* by gbrain's `enrich/SKILL.md` ("a brain page should read like an intelligence dossier, not a LinkedIn scrape… what do they believe, what are they building").
- **The `resolver` as a routing table for context** — "when task type X appears, load document Y first"; "the description *is* the resolver." ([[sources/garrytan--thin-harness-fat-skills#resolvers]], [[sources/garrytan--thin-harness-fat-skills#description-is-the-resolver]]) Grounds [[patterns/composition/resolver-routing-table]] — grounded in the real repos by gbrain's `RESOLVER.md` (a literal trigger→skill table) and gstack's `scripts/resolvers/` + the three resolver evals.
- **The "codify everything / never do one-off work" discipline** and the self-rewriting skill loop — the behavioral engine behind [[patterns/quality-bar/complexity-ratchet]] (the forward-only ratchet: each session writes rules back into the skill file so the next run is better). ([[sources/garrytan--thin-harness-fat-skills#codify-everything]], [[sources/garrytan--thin-harness-fat-skills#learning-loop]], [[sources/garrytan--thin-harness-fat-skills#permanent-upgrades]])
- **The "harness is the product" thesis with a concrete data point** — the Anthropic Claude Code npm source-leak ("March 31, 2026… 512,000 lines") as Garry's evidence that the wrapper, not the model, is the differentiator. A useful, datable external event. ([[sources/garrytan--thin-harness-fat-skills#harness-is-the-product]])

## Contradictions & tensions (for LINT)

1. **OpenClaw authorship (consistent with the known correction).** This essay says *"an instruction I gave to my OpenClaw"* ([[sources/garrytan--thin-harness-fat-skills#codify-everything]]) — i.e., Garry *uses/operates* an OpenClaw. Sibling #8 establishes that **OpenClaw is Peter Steinberger's harness**, not Garry's ([[sources/garrytan--foxconn-factories#openclaw]]). No contradiction *within* this essay (he says "my OpenClaw," meaning his deployment/instance, not that he built it), but it reinforces the existing wiki flag that `garrytan/openclaw` is most plausibly Garry's **fork/deployment** of Steinberger's harness — see the open item on [[creators/garry-tan]] and [[sources/garrytan--gbrain]]. Keep tracking.
2. **"Read-only by default" harness vs. self-rewriting skills.** The architecture insists the harness is *"read-only by default"* ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]]), yet the `/improve` loop has the model *"write… rules back into the matching skills"* and "the skill rewrites itself" ([[sources/garrytan--thin-harness-fat-skills#learning-loop]]). Reconcilable (read-only refers to the *deterministic tool/harness layer* touching *your data/repo*, not to the agent editing its *own skill markdown* under human approval), but a careful reader could see tension — worth a sentence when [[patterns/structural/thin-harness-fat-skills]] and [[patterns/quality-bar/complexity-ratchet]] are written so the boundary is stated explicitly.
3. **Pro-test/forward-only stance vs. the "Foxconn factory" self-audit in #8.** This essay is unreservedly pro-codification and pro-cron ("codify everything") and the series elsewhere celebrates ~276K lines of *tests* ([[sources/garrytan--foxconn-factories#factory-audit]]); yet #8's central metaphor warns against bolting a huge code factory onto a capable model. The reconciliation (tests/skills that *enable change* vs. code that *polices a capable worker*) is the series' through-line, but the surface tension between "codify/test everything" here and "stop building Foxconn factories" in #8 is exactly the kind of thing LINT should keep flagged until the synthesis essay resolves it.
4. **Tokenmaxxing (#8) vs. context-frugality (here).** This essay's whole spine is *minimizing* what hits the context window (the 20,000→200-line CLAUDE.md cut; "context bloat minimization"; resolvers to avoid "polluting the context window") ([[sources/garrytan--thin-harness-fat-skills#twenty-thousand-line-claude-md]], [[sources/garrytan--thin-harness-fat-skills#harness-is-the-product]]). #8 preaches spending *freely* on tokens ([[sources/garrytan--foxconn-factories#tokenmaxxing]]). Likely reconcilable (spend tokens *generously across runs/sub-agents*, but keep any *single* context window *clean*), but it is a genuine same-author tension already tracked from gbrain's cost-rationing banner — note it here too.
