## Anchor map

### root

Defines a harness as software translating a model into an environment-affecting system: looping, context, orchestration, tools, verification and permissions. Conceptual taxonomy, not a supplied runtime.

### context-memory

Context window management inside a run differs from cross-session memory. Procedural skills and broader MEMORY.md/USER.md notes are examples; claims about continual learning are speculative, not evidence of weight changes during ordinary sessions.

### orchestration

Planning/dispatch: delegation scales work but fragments state and introduces overwrite, loop and lost-task risks. Particular plan-file/approval descriptions are article generalizations, not verified current contracts for every named harness.

### tools-authority

Execution versus interface: the harness turns model tool requests into actual actions. Browser access and OAuth-backed read/draft/send capabilities expose different authorization boundaries. MCP is optional, with CLI/docs alternatives.

### verification

Warns that implementation-aware unit tests can become low-signal and argues for exercising the resulting product. This is not evidence that tests are generally useless or that an extra reviewer proves correctness.

### permissions

Permission checks belong in harness execution; prompt, automatic reviewer and human escalation are described at a broad level. The article does not establish universal current behavior or complete safety of an LLM gate.

### claims-limits

External speed/cost/puzzle links and predictions about verification emerging from training were not independently checked in this ingest; no 18× or superhuman claim is used as evidence of always-on agent usefulness.
