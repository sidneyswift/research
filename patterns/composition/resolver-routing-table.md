# resolver-routing-table

> A **resolver** is a routing table for context: *when task/intent/content-type X appears, load skill-or-document Y first.* It replaces cramming everything into the system prompt with a small (~200-line) load-on-demand index — one that is **tested** with trigger evals (false-negative *and* false-positive cases), **audited** for reachability with `check-resolvable`, and is **fractal** (the same shape recurs at the skill layer, the filing layer, and inside individual skills).

## Longer definition

Garry Tan reframes the resolver as the **governance / management layer** of an agent "organization": if skills are the employees, the resolver is the org chart plus the escalation logic, the filing rules are process, `check-resolvable` is the audit, and trigger evals are the performance reviews ([[sources/garrytan--resolvers#management-metaphor]]). The thing it operates on is *attention* — it decides which of N skills or documents the model reads *before* it starts a task, so the system prompt can stay thin and the heavy material stays load-on-demand. What it produces is reachability and consistency: every built skill has a path that fires it, and shared decisions (where a file goes, which skill owns an intent) are made **once** in the table instead of being re-invented inside each skill. A creator reaches for it the moment a skill pack grows past the size where Claude Code's built-in description-matching resolves cleanly — because past that point three failures appear that the resolver exists to kill. First, skills invent their own filing logic and **drift** ([[sources/garrytan--resolvers#filing-mandate]]). Second, a skill can *exist but be unreachable* — "a surgeon the hospital can't find," the essay's **invisible skill** ([[sources/garrytan--resolvers#invisible-skill]]). Third, the table itself **rots** within roughly 90 days of [[patterns/quality-bar/complexity-ratchet|context-rot]] unless it learns from its own traffic ([[sources/garrytan--resolvers#context-rot]]). The resolver is the single artifact whose whole job is to prevent those three.

## Mechanism

There are **two philosophies** for where the routing table lives, and the wiki has a worked example of each.

**Explicit resolver (gbrain).** gbrain ships the machinery almost line-for-line from the essay:

- `skills/RESOLVER.md` is the literal `trigger → skill` dispatcher, read once per request. Its opening line states the contract: *"This is the dispatcher. Skills are the implementation. **Read the skill file before acting.** If two skills could match, read both."* The body is markdown tables grouped by domain (`"What do we know about" / "who is" / "background on" → skills/query/SKILL.md`), exactly the ~200-line load-on-demand index the pattern describes ([[sources/garrytan--gbrain#skills-resolver]]).
- `skills/_brain-filing-rules.md` is a *second* resolver — a `content-type → directory` filing table — that hoists one rule above all the skills: *"The PRIMARY SUBJECT of the content determines where it goes. Not the format, not the source, not the skill that's running."* It then enumerates "Common Misfiling Patterns — DO NOT DO THESE." This is the "one shared rule beats N hardcoded defaults" move made concrete ([[sources/garrytan--gbrain#skills-brain-filing-rules]], [[sources/garrytan--resolvers#filing-mandate]]).
- **15 `routing-eval.jsonl` fixtures** (one per skill: `query/`, `citation-fixer/`, `frontmatter-guard/`, `functional-area-resolver/`, …) encode `{intent, expected_skill, ambiguous_with?}`. The `query` fixture's header even pins a discipline — *"intent must paraphrase the trigger, not copy it"* — so the eval tests routing, not string-matching. Crucially these carry **both polarities**: positive intents that *must* fire a skill, and "adversarial negative fixtures at the bottom [that] guard against the broadened triggers over-capturing intents that belong to adjacent meta-skills." That is the false-negative + false-positive coverage the short definition demands ([[sources/garrytan--gbrain#skill-citation-fixer]]).
- `src/commands/check-resolvable.ts` (thin CLI over `src/core/check-resolvable.ts`, with `test/check-resolvable.test.ts` and `test/check-resolvable-cli.test.ts`) is the **audit**: it walks the manifest and *"Check[s] every manifest skill is reachable from RESOLVER.md,"* tracking `reachable` / `unreachable` / `orphan_trigger`, plus MECE-overlap, MECE-gap, and DRY checks. An unreachable skill is a hard finding — this is the literal detector for the "invisible skill" anti-pattern ([[sources/garrytan--resolvers#check-resolvable]], [[sources/garrytan--resolvers#invisible-skill]]).
- `skills/functional-area-resolver/` is a resolver **inside a skill**: a skill whose job is to compress an over-large `RESOLVER.md` into functional areas, shipped with its own `routing-eval.jsonl` and A/B eval results ("D5:B" broadened-trigger variants). It is the [[sources/garrytan--resolvers#fractal|fractal]] property as a file you can open ([[sources/garrytan--gbrain#skill-functional-area-resolver]]).

**Description-as-resolver + preamble compiler (gstack).** gstack leans on Claude Code's *native* mechanism — the skill's `description` frontmatter field *is* the resolver, and the harness auto-triggers on it ([[sources/garrytan--thin-harness-fat-skills#description-is-the-resolver]]). On top of that it runs `scripts/resolvers/` — a **preamble compiler** (`preamble.ts`, `composition.ts`, `confidence.ts`, `gbrain.ts`, plus `preamble/` fragments) that assembles the routing context — and proves the routing with **three resolver evals**: `test/resolver-ask-user-format.test.ts`, `test/writing-style-resolver.test.ts`, `test/resolvers-gbrain-put-rewrite.test.ts` ([[sources/garrytan--gstack#test]]). Same job (decide which skill fires, then test that decision), opposite locus: gbrain reads an explicit file once per request; gstack rides the harness's description match and compiles a preamble.

The reusable shape, either way: **(1)** a small index mapping trigger→target, **(2)** a polarity-balanced eval that fires the right thing and *refuses* the wrong thing, **(3)** a reachability audit so nothing is dark, and **(4)** acceptance that the table is fractal and will need re-compression as it grows.

## When to use

- The skill pack is **big enough that description-only auto-triggering misses or mis-fires.** The essay's threshold is concrete: ~40+ skills / 13+ writers is where Garry says the implicit mechanism stops being reliable and an explicit, tested routing layer earns its keep ([[sources/garrytan--resolvers#the-audit]], [[sources/garrytan--resolvers#the-20000-line-confession]]).
- **Filing / routing must be consistent across many skills.** One shared `_brain-filing-rules.md` ("primary subject decides") beats N skills each hardcoding their own default directory — and prevents the drift that the filing mandate exists to stop ([[sources/garrytan--gbrain#skills-brain-filing-rules]], [[sources/garrytan--resolvers#filing-mandate]]).
- You need to **prove the right skill fires** — ship `routing-eval.jsonl` trigger evals with positive *and* adversarial-negative cases ([[sources/garrytan--gbrain#skill-citation-fixer]], [[sources/garrytan--skillify-manifesto#step7-resolver-eval]]).
- You need to **prove every built skill is reachable** — run `check-resolvable` so a skill that was authored but never wired into the table fails the build instead of going silently dark ([[sources/garrytan--resolvers#check-resolvable]], [[sources/garrytan--skillify-manifesto#step8-check-resolvable-dry]]).
- The agent operates across a **jagged frontier** where some intents need a deterministic hand-off and the bare model would otherwise guess — the resolver is where you encode "for *this* class of request, load *that* skill first" ([[sources/garrytan--naked-models#jagged-frontier]]).

## When NOT to use

- **A handful of skills that Claude Code's built-in description-matching already resolves cleanly.** Below the threshold, an explicit `RESOLVER.md` is pure overhead — it's a second place routing can be wrong. Anthropic's demonstration skills are the reference case: small set, description-only, no resolver file, and that is *correct* (cf. [[artifacts/plugins/anthropic-skills-marketplace]]).
- **You cannot maintain the table.** A stale resolver is *worse* than none: it advertises capabilities that no longer route, sending the agent to a skill that moved or was deleted. The whole [[sources/garrytan--resolvers#context-rot|context-rot]] section is the warning — if no one (human or RLM) will keep the table honest against its own traffic, don't ship one ([[sources/garrytan--resolvers#context-rot]]).
- **Very early exploration, before the skill set stabilizes.** Writing trigger evals and a dispatcher around skills you'll delete next week is premature; the resolver is a *graduation* step (essay's step 6–8), applied after a capability proves worth keeping ([[sources/garrytan--skillify-manifesto#step6-resolver-trigger]]).
- **When the routing genuinely is unambiguous and 1:1.** If each intent maps to exactly one obviously-named skill with no overlap, the description field already does the job; the MECE-overlap machinery in `check-resolvable` is solving a problem you don't have.

## Why it works

The resolver works because of how Claude Code loads context: the system prompt is finite and *always* paid for, but skills are loaded on demand — so the cheapest way to scale capability is to keep the prompt thin and push everything else behind a small index that says *which* heavy thing to load *when*. Garry's framing is that you are managing an organization, not writing one giant prompt: *"You don't put the entire org chart in every employee's head; you give them an escalation path"* — and the resolver is that escalation path, read once per request, costing ~200 lines instead of the [[sources/garrytan--resolvers#the-20000-line-confession|20,000-line]] system prompt the essay confesses to having grown ([[sources/garrytan--resolvers#management-metaphor]], [[sources/garrytan--resolvers#the-20000-line-confession]]). It survives contact with a real, growing skill pack because of three reinforcing tests aligned with the [[patterns/quality-bar/complexity-ratchet|complexity ratchet]]: trigger evals make "does the right skill fire?" a *runnable* question with both polarities, so broadening a trigger to catch one intent can't silently capture three others ([[sources/garrytan--skillify-manifesto#step7-resolver-eval]]); `check-resolvable` makes "is anything dark?" a build gate, so a surgeon the hospital can't find is a CI failure not a production surprise ([[sources/garrytan--resolvers#check-resolvable]]); and the fractal property means the *same* tested-index discipline applies recursively — at the skill layer (`RESOLVER.md`), the filing layer (`_brain-filing-rules.md`), and inside a single skill (`functional-area-resolver/`) — so you learn the mechanism once and reuse it at every altitude ([[sources/garrytan--resolvers#fractal]]). The essay's endgame is that the routing table eventually rewrites *itself* from observed traffic, which is the only durable answer to context-rot ([[sources/garrytan--resolvers#context-rot]]); the gbrain/gstack examples ship everything up to that self-healing step.

## Examples in this wiki

- [[artifacts/plugins/gbrain]] — **the explicit-resolver exemplar.** `skills/RESOLVER.md` is a literal `trigger → skill` dispatcher ("read the skill file before acting"); `skills/_brain-filing-rules.md` is the `content-type → directory` filing resolver ("primary subject decides, not the format/source/skill"); 15 `routing-eval.jsonl` fixtures encode `{intent, expected_skill, ambiguous_with?}` with explicit *adversarial negative* cases; `src/commands/check-resolvable.ts` walks the manifest and flags any skill not reachable from `RESOLVER.md`; and `skills/functional-area-resolver/` is a resolver *inside* a skill, shipped with its own A/B eval. — citation: [[sources/garrytan--gbrain#skills-resolver]], [[sources/garrytan--gbrain#skills-brain-filing-rules]], [[sources/garrytan--gbrain#skill-citation-fixer]], [[sources/garrytan--gbrain#skill-functional-area-resolver]], [[sources/garrytan--resolvers#check-resolvable]]
- [[artifacts/plugins/gstack]] — **the description-auto-trigger + preamble-compiler exemplar.** It leans on Claude Code's native mechanism — the `description` field *is* the resolver, auto-triggered by the harness — and adds `scripts/resolvers/` as a preamble compiler, then proves the routing with three resolver evals (`resolver-ask-user-format`, `writing-style-resolver`, `resolvers-gbrain-put-rewrite`). Same problem as gbrain, solved at the harness layer rather than in an explicit file. — citation: [[sources/garrytan--gstack#test]], [[sources/garrytan--thin-harness-fat-skills#description-is-the-resolver]]

> **Caveat the wiki tracks:** both confirmed examples are **the same creator's** (Garry Tan, gbrain + gstack). They count as two *distinct artifacts* — and they deliberately demonstrate the *two opposite philosophies* (explicit file vs. native description-match), which is stronger than two copies of one approach — but a single author proving a house style twice is weaker than two independent creators. The promotion gate that would harden this to fully-independent confirmation is a **non-Garry skill pack** that converges on an explicit, polarity-balanced resolver eval (the rare part) rather than relying on description-auto-trigger alone.

## Counter-examples or anti-pattern

- [[artifacts/plugins/anthropic-skills-marketplace]] — relies **purely** on Claude Code's built-in description-field auto-trigger: no explicit `RESOLVER.md`, no `routing-eval.jsonl`, no reachability audit. This is *correct* for a small demonstration set whose consumer is a human studying the format — and it is genuinely the **degenerate (built-in) case** of this very pattern: the resolver still exists, it's just the harness's implicit description-matcher rather than a file. The reason it's a counter-example and not an example is the resolvers essay's whole thesis: this implicit mechanism *silently breaks at 40+ skills* — dark skills accumulate and routing turns ambiguous with no test to catch either ([[sources/garrytan--resolvers#the-audit]]). The marketplace is the "before" state the pattern is a response to.
- **The "invisible skill" (in-essay anti-pattern).** Garry's own audit found a signature/email-signature tracker that was fully built but had **no trigger** wiring it into the resolver — so it never fired. *"A skill that exists but cannot be reached is a surgeon the hospital can't find."* This is the failure mode `check-resolvable` was written to detect, and the canonical example of why "I wrote the skill" ≠ "the agent can reach the skill" ([[sources/garrytan--resolvers#invisible-skill]]).

## Open questions

- **Independence.** Both confirmed examples are Garry's. Does a non-Garry skill pack at comparable scale (40+ skills) converge on an *explicit* resolver + polarity-balanced trigger evals — or is Claude Code's description-auto-trigger actually sufficient at everyone else's scale, making the explicit `RESOLVER.md` a Garry-specific response to a Garry-specific 20K-line history? Finding one independent case either way would resolve the central confidence question.
- **Is self-healing shipped or aspirational?** The essay's endgame — an RLM that *rewrites the resolver from its own traffic* — is stated as the durable answer to context-rot ([[sources/garrytan--resolvers#context-rot]]). The gbrain/gstack artifacts ship the *tested static* table and the audit, but is the traffic-driven rewrite an actual running loop anywhere, or a roadmap? Claude Code's **AutoDream** is named as a primitive version of the idea ([[sources/garrytan--meta-meta-prompting#architecture]]) — worth tracing whether it closes the loop.
- **Where does the threshold actually sit?** "~40 skills / 13 writers" is one creator's observed breaking point ([[sources/garrytan--resolvers#the-audit]]). Is the real driver *count*, *trigger ambiguity* (overlapping descriptions), or *content-type fan-out* (the filing problem)? `check-resolvable`'s MECE-overlap output is the instrument that could answer this empirically.
- **Does `check-resolvable` close the full loop?** Its own header notes it currently covers 4 of 6 designed checks — reachability, MECE overlap, MECE gap, DRY — and *defers* Check 5 (trigger routing eval) and Check 6 (brain filing) to the separate `routing-eval.jsonl` / filing machinery. So "audited for reachability" is live, but "audited end-to-end" is split across tools; worth tracking whether they're ever unified into one gate.
