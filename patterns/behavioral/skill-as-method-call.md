# skill-as-method-call

> A skill file is a **parameterized markdown procedure, invoked like a method call**: the user supplies the *what* (the arguments — a TARGET, a QUESTION, a DATASET, or a depth tier), the skill supplies the *how* (the fixed process). The same markdown yields radically different capabilities depending on what you pass in — one `/investigate` is a medical-research analyst over 2.1M discovery emails *or* a forensic investigator over FEC filings; one `/qa` is Quick *or* Exhaustive.

## Longer definition

This pattern reframes "a skill" from a one-purpose macro into a **reusable function whose generality comes from parameterization**. Garry Tan states it almost in those exact terms: a skill file "works like a method call… takes parameters" ([[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]]), and "same procedure, radically different outputs depending on what you pass in" — the user supplies the *what*, the skill supplies the *process* ([[sources/garrytan--skillify-manifesto#skill-as-method-call]]). The skill body is the *how* (the steps, the contract, the tools-it-may-touch); the invocation is the *what* (the subject, the dataset, the depth). It is "software design, using markdown as the programming language and human judgment as the runtime" ([[sources/garrytan--thin-harness-fat-skills#skill-files]]). The payoff is leverage: a well-parameterized skill amortizes its design cost across many invocations and — because it has a stable signature — *composes* with other skills as a pipeline step (gbrain's `book-mirror` calls `enrich`, `brain-ops`, `cross-modal-eval`, and `pdf-generation` rather than re-implementing them — [[sources/garrytan--meta-meta-prompting#skills-compose]]).

## Mechanism

A skill written this way separates two things the naive "one skill = one task" macro fuses: the **invariant procedure** (lives in the markdown) and the **per-call arguments** (supplied at invocation). Concretely, in the real repos:

1. **A depth argument that changes thoroughness, not procedure** — gstack's `qa/SKILL.md` ships an explicit tier parameter in its own description: "Three tiers: Quick (critical/high only), Standard (+ medium), Exhaustive (+ cosmetic)" ([[sources/garrytan--gstack#qa]]). One file, one process; the `--quick` / `--exhaustive` argument selects *which severities get fixed* and *how deep the page-walk goes* — the QA loop itself is unchanged. This is the cleanest in-repo instance of a "parameter," because the parameter is named and documented.
2. **A subject/target argument that re-aims a fixed procedure** — gstack's `investigate/SKILL.md` is a fixed multi-phase procedure ("Four phases: investigate, analyze, hypothesize, implement. Iron Law: no fixes without root cause" — [[sources/garrytan--gstack#investigate]]) whose *behavior is entirely determined by the bug/target/question handed to it*. The seven (in the essay) or four (in the repo) steps never change; the error, the stack trace, the codebase are the arguments. This is the repo grounding for the essays' canonical `/investigate(TARGET, QUESTION, DATASET)` narrative — "Same skill. Same seven steps," different world ([[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]]) — and for the three `/match-*` invocations of *one* matching procedure (`/match-breakout` vs `/match-lunch` vs `/match-live`, same skill, different cohort/constraints in — [[sources/garrytan--thin-harness-fat-skills#match-skills]]).
3. **Composition via a declared dependency** — because a parameterized skill has a stable "signature," other skills can *call* it. gstack encodes this with a `benefits-from:` frontmatter field (`autoplan`, `plan-ceo-review`, `plan-eng-review`, `plan-devex-review` all declare `benefits-from: [office-hours]` — [[sources/garrytan--gstack#root]]), and gbrain's `book-mirror` is an explicit pipeline that composes lower-level skills as steps rather than inlining them ([[sources/garrytan--meta-meta-prompting#skills-compose]]). The same essay frames the *creation* of such skills as itself a method call — "skillify it" extracts the repeatable pattern into a tested skill ([[sources/garrytan--meta-meta-prompting#skills-that-build-skills]]) — i.e. the factory that mints these functions is one too.

The decomposition discipline underneath is the same one `#bathroom-decompose` describes: a skill is a *decomposed* procedure — "The model does the judgment. The code does the execution. The resolver routes between them. The harness orchestrates the sequence" ([[sources/garrytan--naked-models#bathroom-decompose]]). Parameterization is what lets that one decomposition be re-run against many inputs instead of re-authored per input.

## When to use

- **A process that generalizes across many "worlds"** — the same steps applied to a different subject, dataset, or depth: investigations, code reviews, QA passes, matching/clustering, enrichment, ingestion. If you can describe the task as "do *this fixed thing* to *whatever I hand you*," it wants a parameter.
- **When you would otherwise copy-paste a skill and tweak it.** Two skills that differ only in their input (or in a depth knob) are one parameterized skill. `/match-breakout`, `/match-lunch`, `/match-live` are the canonical "don't fork it, parameterize it" case ([[sources/garrytan--thin-harness-fat-skills#match-skills]]).
- **A depth/thoroughness dial** where the procedure is identical but the cost/coverage tradeoff varies per call — gstack's Quick/Standard/Exhaustive `/qa` tiers ([[sources/garrytan--gstack#qa]]).
- **When skills should compose into pipelines.** A skill with a stable signature can be called by another skill as a step (`book-mirror` → `enrich`/`brain-ops`/`cross-modal-eval`/`pdf-generation` — [[sources/garrytan--meta-meta-prompting#skills-compose]]); a one-off macro cannot be reused this way without copy-paste.

## When NOT to use

- **A genuinely single-purpose skill.** If the skill does exactly one thing to one kind of input and will never be re-aimed, parameterization is *fake generality*: it adds a layer of indirection and cognitive load (a reader now has to figure out which "mode" they're in) for no reuse. Most skills in this wiki are correctly *not* parameterized — see Counter-examples.
- **When the "parameters" actually change the *process*, not the input.** This is the diagnostic test. If passing argument A runs steps 1–4 and argument B runs a *different* set of steps, those are **two different skills wearing one filename**, not one method with two arguments. A true argument varies the *what* while the *how* stays fixed (the `/qa` tier still runs the QA loop; the `/investigate` phases don't change with the bug). The failure mode of ignoring this is the **god-skill**: one file with a dozen modes and ambiguous routing that no resolver can dispatch cleanly.
- **Early exploration.** Don't design the parameter signature before you've run the procedure manually a few times — Garry's own workflow is to do the thing first, *then* "skillify it" once the repeatable shape is visible ([[sources/garrytan--meta-meta-prompting#skills-that-build-skills]]). Premature parameterization locks in arguments you don't understand yet.

## Why it works

It works because of how Claude Code actually consumes a skill: the markdown is *prompt content the model reads and follows as instructions*, not compiled logic. That makes the natural-language procedure the durable, reusable unit and the invocation the variable — exactly the shape of a function call, which is why the "method call" metaphor is load-bearing rather than decorative. Three properties of the runtime make it pay off:

1. **The model is the runtime that binds the arguments.** "Human judgment as the runtime" ([[sources/garrytan--thin-harness-fat-skills#skill-files]]) means the model can take an under-specified argument (a messy bug report, an unfamiliar dataset) and still execute the fixed procedure against it — something a literal typed function cannot do. The procedure is fixed; the *interpretation* of the argument is latent. This is why one `/investigate` can be "a safety scientist over 2.1M discovery emails" *or* "a forensic investigator over FEC filings" with no code change ([[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]]).
2. **A stable signature is what makes skills composable and improvable.** Because the call shape is stable, other skills can depend on it (`benefits-from:`, the `book-mirror` pipeline) — and, as the essay puts it, "When I improve one skill, every workflow that uses it gets better automatically" ([[sources/garrytan--meta-meta-prompting#skills-compose]]). That compounding only exists because the unit is a *reused function*, not a *forked copy*.
3. **A parameter that selects depth is a clean knob for the latent/deterministic cost tradeoff.** gstack's Quick/Standard/Exhaustive tiers ([[sources/garrytan--gstack#qa]]) let one skill expose "cheap-and-shallow vs thorough-and-expensive" without two implementations — a single dial over the same procedure, which is precisely what a method argument is for.

## Examples in this wiki

- [[artifacts/projects/codex-goals]] — **the textbook example, and the one that promoted this pattern (non-Garry).** OpenAI's Codex `/goal` ships an *explicit, documented parameter signature*: `/goal <desired end state> verified by <specific evidence> while preserving <constraints>. Use <allowed inputs, tools, or boundaries>. Between iterations, <how to choose the next best action>. If blocked, <what to report and what would unlock progress>.` Same command, radically different objective depending on the six arguments you bind — the cleanest "method call with named args" in the wiki, and the first from outside Garry Tan's corpus. — citation: [[sources/openai--using-goals-in-codex#goal-template]], [[sources/openai--using-goals-in-codex#six-elements]].
- [[artifacts/plugins/gstack]] — **the first in-wiki example (lightly parameterized).** Two of its skills are recognizable method-calls: `/qa` carries an explicit named *depth* argument (Quick / Standard / Exhaustive) that changes thoroughness from one file, and `/investigate` is a fixed four-phase procedure whose behavior is entirely determined by the bug/target passed in. gstack also makes skills *callable by other skills* via `benefits-from:` frontmatter. — citation: [[sources/garrytan--gstack#qa]], [[sources/garrytan--gstack#investigate]], [[sources/garrytan--gstack#root]], and the author's articulation [[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]] (the `/investigate(TARGET,QUESTION,DATASET)` and `/match-*` narrative).
- *Composition corroboration (same creator, different repo):* [[artifacts/plugins/gbrain]] — `book-mirror` composes `enrich` + `brain-ops` + `cross-modal-eval` + `pdf-generation` as a pipeline, which only works because each is a callable, stably-signed unit. — citation: [[sources/garrytan--meta-meta-prompting#skills-compose]].
- *Articulations (not artifacts):* [[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]] ("works like a method call… takes parameters"); [[sources/garrytan--skillify-manifesto#skill-as-method-call]] ("same procedure, radically different outputs depending on what you pass in"); [[sources/garrytan--naked-models#bathroom-decompose]] (a skill = a decomposed, re-runnable procedure).

> **Promoted to `confirmed` 2026-06-02.** This page previously sat `proposed` with a precise gate: *"a 2nd example sufficient to promote this would be a skill that ships an explicit, documented parameter signature (named arguments in its frontmatter or contract, not just 'whatever you hand it'), ideally from a non-Garry pack."* [[artifacts/projects/codex-goals]] clears it exactly — Codex `/goal` ships a literal six-slot signature ([[sources/openai--using-goals-in-codex#goal-template]]), and it's **OpenAI**, not Garry Tan, which also breaks the single-creator caveat that still constrains the sibling pattern [[patterns/quality-bar/skill-pack-bundle]]. The two grounding artifacts now span two creators *and* two harnesses (gstack on Claude Code, Codex Goals on the Codex CLI), so the pattern isn't an artifact of one toolchain. gstack remains the *lightly*-parameterized end of the spectrum (`/qa` tiers are a named arg; `/investigate` just consumes its target); Codex Goals is the *explicit-signature* end.

## Counter-examples or anti-pattern

- [[artifacts/plugins/anthropic-skills-marketplace]] — Anthropic's demonstration skills are **single-purpose**, not parameterized method-calls: each `SKILL.md` shows one capability and one shape, for a human reader studying the format. That is the **correct default** — most skills *should not* be parameterized, because parameterization is a deliberate design move reserved for procedures that genuinely recur across different inputs. Many of gstack's and gbrain's own skills are likewise single-purpose. The lesson: "method call" is the exception you reach for when a process generalizes, not a goal to retrofit onto every skill.
- **The god-skill (the inverse failure).** Over-applying this pattern yields one file with a dozen "modes," where the arguments secretly select *different procedures* and the resolver can't route cleanly. The tell is when adding a new "mode" means adding new steps rather than handling a new input through the *same* steps — at that point you have several skills crammed into one signature, and you should split them. The `/match-*` family deliberately went the *other* way: three separate invocations of one genuinely-shared procedure, not one mega-`/match` with a `mode=` flag ([[sources/garrytan--thin-harness-fat-skills#match-skills]]).

- [[patterns/composition/resolver-routing-table]] — composes-with: the resolver is what *routes the call to the right "method"* (and, for a parameterized skill, must dispatch cleanly despite multiple modes — the god-skill is precisely where resolver routing breaks down).
