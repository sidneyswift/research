# thin-harness-fat-skills

> Put ~90% of a system's capability in **fat markdown skills** at the top, push execution **down** into narrow deterministic code at the bottom, and keep the **harness** in the middle thin (~200 lines: loop the model, read/write files, manage context, enforce safety — JSON-in / text-out, read-only by default). The directional rule is "push intelligence up, push execution down, keep the harness thin."

## Longer definition

This is the namesake architecture of Garry Tan's 8-part "AI Explainer" series and its single load-bearing claim: the gap between a "2x" and a "100x" AI engineer running *the same models* "isn't intelligence — it's architecture, and it fits on an index card" ([[sources/garrytan--thin-harness-fat-skills#index-card-thesis]]). The system is three layers. **Top:** fat skills — reusable markdown procedures that teach the model *how*, where ~90% of the value lives ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]]). **Bottom:** a deterministic application — same input, same output: SQL, compiled binaries, arithmetic, the things the model must never improvise. **Middle:** a thin harness that "does four things: run the model in a loop, read/write files, manage context, enforce safety — that's the thin" ([[sources/garrytan--thin-harness-fat-skills#the-harness]]). A creator reaches for this split because of what it *buys over time*: improving the model "instantly" lifts every skill (the judgment in the latent steps gets better) "while the deterministic steps stay perfectly reliable" ([[sources/garrytan--thin-harness-fat-skills#permanent-upgrades]]). Capability lives in editable prose, not logic frozen in code, so it can be revised; the substrate stays a contract.

The pattern is defined as much by its **inverse** as by its shape. The anti-pattern is a *fat harness wrapping thin skills*: "40+ tool definitions" eating the context window, god-tools, a REST-wrapper-per-endpoint, slow generic transports — which the essay quantifies as "3× tokens, 3× latency, 3× failure rate" ([[sources/garrytan--thin-harness-fat-skills#the-harness]]). When the wrapper, not the skill, holds the intelligence, you lose the free model upgrade *and* pay the tax on every call. Note the deliberate asymmetry in the name: the harness is thin, but the *code* layer is allowed to be fat — narrow, fast, deterministic tools are a feature; a fat *harness* is the failure.

## Mechanism

In gstack the three-layer split is literal and inspectable:

1. **Deterministic foundation (bottom).** `bin/` holds ~60 single-purpose CLIs (the source page's `#bin` anchor counts 62) — each a narrow deterministic helper (`gstack-diff-scope`, `gstack-config`, `gstack-analytics`, `chrome-cdp`, the `gstack-brain-*` family) rather than one generic god-tool ([[sources/garrytan--gstack#bin]]). Alongside it, `browse/` is a compiled programmable-browser tool (its own `src/`, `bin/`, and a ~100-file test suite) — the embodiment of the essay's purpose-built-tool claim: a Playwright-style CLI at ~100 ms/op versus a Chrome MCP at ~15 s for the screenshot→find→click→wait→read loop = "75x faster… software doesn't have to be precious anymore" ([[sources/garrytan--thin-harness-fat-skills#playwright-cli-75x]]).
2. **Fat skills (top).** The capability is authored as markdown `SKILL.md` procedures sitting *on top* of that substrate — `investigate/SKILL.md`, the `plan-*-review/` family, `qa/`, `cso/`, `ship/`. These are where the judgment lives; they decide *what* to look up and call the deterministic layer to decide *how*.
3. **Thin harness (middle).** Crucially, the harness — "the loop that runs the model" — is **not gstack itself**. gstack is *harness-agnostic*: it runs inside OpenClaw / Hermes / Claude Code / Codex, whichever conductor the operator points at it ([[sources/garrytan--meta-meta-prompting#architecture]], [[sources/garrytan--meta-meta-prompting#models-interchangeable]]). The series describes routine production as "15 simultaneous Conductor sessions… Claude Code and Codex at my direction" — multiple harnesses, one skill layer ([[sources/garrytan--complexity-ratchet#conductor-sessions]]). The harness's defining property in the architecture is its *thinness*: "about 200 lines… JSON in, text out. Read-only by default" ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]]). In #6 the same harness (OpenClaw) is described as "a few thousand lines of routing logic… It just routes" ([[sources/garrytan--meta-meta-prompting#architecture]]).

gbrain shows the same skeleton in a different domain: a 53-entry markdown **skillpack scaffold** (`skills/`) over a thin compiled gbrain **CLI** (the `#bin` binary) plus the deterministic graph/vector engine underneath ([[sources/garrytan--gbrain#README]], [[sources/garrytan--gbrain#bin]]). Same move: fat skills on top, thin CLI in the middle, deterministic app at the bottom.

The "five definitions" the series builds on are the components this architecture wires together — skill files, the thin harness, resolvers, the latent-vs-deterministic split, and diarization ([[sources/garrytan--thin-harness-fat-skills#five-definitions]]) — and the inverse fat-harness failure is named in [[sources/garrytan--thin-harness-fat-skills#the-harness]]. The directional law is one sentence: "push intelligence up, push execution down, keep the harness thin" ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]]).

## When to use

- **The capability will be edited and extended over time.** Behavior in editable prose beats logic frozen in code; the whole point is that a maintainer (human or agent) revises the markdown without recompiling ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]]).
- **The system must outlive any one model.** When the next model drops, the judgment in every latent step improves for free while the deterministic steps stay perfectly reliable — the architecture is how you bank model progress ([[sources/garrytan--thin-harness-fat-skills#permanent-upgrades]]). The complementary claim: don't cram intelligence into a fat system prompt — the resolver/skill layer loads it on demand ([[sources/garrytan--resolvers#the-20000-line-confession]]).
- **You control the deterministic substrate** and can build *narrow, fast* tools instead of generic god-tools — the Playwright-CLI-vs-Chrome-MCP gap (75x) is the payoff for owning the bottom layer ([[sources/garrytan--thin-harness-fat-skills#playwright-cli-75x]]).
- **You want the same skills to run across multiple runtimes.** Because the harness is thin and interchangeable, one fat-skill layer targets Claude Code, Codex, OpenClaw, or Hermes without a rewrite ([[sources/garrytan--complexity-ratchet#conductor-sessions]], [[sources/garrytan--meta-meta-prompting#models-interchangeable]]).

## When NOT to use

- **A one-shot script.** If a task runs once and is discarded, the three-layer split is pure overhead — you don't need a skill, a resolver, and a deterministic substrate to do something twice. (The series' own discipline gates codification behind proven, repeated use: "do it manually the first time on 3 to 10 items," *then* codify — [[sources/garrytan--thin-harness-fat-skills#codify-everything]].)
- **Pure chat with no deterministic substrate.** If there is nothing for the bottom layer to do — no SQL, no compiled tool, no arithmetic the model must not improvise — there is no execution to push down, and the architecture collapses to "a skill and a model," which is fine but is not *this* pattern.
- **When the "thin" harness is actually doing the heavy lifting.** If real logic creeps into the middle layer, you have silently rebuilt the fat-harness anti-pattern the essay warns against (40+ tools, god-tools, REST-wrapper-per-endpoint) — and you've lost the free model upgrade ([[sources/garrytan--thin-harness-fat-skills#the-harness]]). Watch this boundary in practice: gstack's *own* root `SKILL.md` preamble is **962 lines** (with `CLAUDE.md` at 887 and `ETHOS.md` at 164), running telemetry, per-project `learnings.jsonl` loading, timeline logging, and routing detection *before any skill logic* ([[sources/garrytan--gstack#SKILL.md]], [[sources/garrytan--gstack#CLAUDE.md]]). That heavy "skill OS" preamble is a genuine tension with the word "thin" — see Counter-examples. If your top layer needs a small CLI app to run before every call, interrogate whether "thin" still describes the system.

## Why it works

It works because it sorts every step by the property that actually predicts reliability — *latent vs. deterministic* — and puts each kind of work where it is safe. "Every step is one or the other; confusing them is the most common mistake in agent design" ([[sources/garrytan--thin-harness-fat-skills#latent-vs-deterministic]]); the 8-vs-800 dinner-seating example shows combinatorial optimization forced into latent space hallucinating, where a deterministic algorithm would be exact. Push the judgment up (it benefits from a better model), push the determinism down (it must never drift), and the harness in the middle has only one job — orchestrate the loop — so keeping it thin keeps the context window clean and the failure surface small ([[sources/garrytan--thin-harness-fat-skills#the-harness]]). The economic engine is the model-upgrade ratchet: skills are "permanent upgrades… and when the next model drops, every skill instantly gets better — the judgment in the latent steps improves while the deterministic steps stay perfectly reliable" ([[sources/garrytan--thin-harness-fat-skills#permanent-upgrades]]). The companion essay states the same idea as a slogan — "the model is the engine, the harness is the car" — and argues that a *naked* model's unreliability is a harness-engineering problem, not a verdict on AI ([[sources/garrytan--naked-models#terms-defined]], [[sources/garrytan--naked-models#engine-on-a-bench]]). And it works because *attention is the scarce resource*: the 20,000-line `CLAUDE.md` that "drowned" the model is the cautionary tale for cramming intelligence into the harness/prompt instead of loading it on demand — "don't cram" ([[sources/garrytan--resolvers#the-20000-line-confession]]).

## Detection recipe

A falsifiable test for spotting the architecture (`## Examples` are the positive fixtures; the fat-harness inverse is the negative test). Note this pattern is still `proposed` — the *middle* layer is the part hardest to confirm:

- **Look for**: a three-layer split — **fat markdown skills on top** (the judgment, ~90% of value), **narrow deterministic code at the bottom** (single-purpose CLIs / compiled tools, *not* a generic god-tool), and a **thin middle harness** that only loops the model / does file I-O / manages context / enforces safety; the skill layer is harness-agnostic (the same skills run in Claude Code / Codex / OpenClaw).
- **Confirm with**: a better model would lift *every* skill for free while the deterministic floor stays fixed (the "permanent upgrade" property); and the harness is genuinely thin — the hard part to verify, so inspect its line count / read-only-ness if the harness is available.
- **Rule out**: the **fat-harness inverse** (40+ tool defs eating context, god-tools, a REST-wrapper-per-endpoint — "3× tokens, 3× latency, 3× failure"); a one-shot script (no substrate to push down to); pure chat with no deterministic bottom; and the leak to watch — a nominally "thin" harness or a heavy skill-OS preamble (gstack's 962-line root `SKILL.md`) that's actually doing the heavy lifting means "thin" no longer describes the system.

## Examples in this wiki

- [[artifacts/plugins/gstack]] — **the one grounded artifact example.** The split is literal: ~60 single-purpose deterministic CLIs in `bin/` (source `#bin` anchor: 62) + the compiled `browse/` programmable-browser tool form the deterministic foundation; markdown `SKILL.md` procedures (`investigate`, `plan-*-review`, `qa`, `cso`, `ship`) are the fat skills on top; and the harness is *not* gstack — it runs inside Claude Code / Codex / OpenClaw, harness-agnostic. — citation: [[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]] (the named architecture), [[sources/garrytan--thin-harness-fat-skills#playwright-cli-75x]] (the `browse/` "75x" purpose-built tool), [[sources/garrytan--complexity-ratchet#conductor-sessions]] (harness-agnostic: 15 Conductor sessions, Claude Code + Codex), [[sources/garrytan--gstack#bin]] + [[sources/garrytan--gstack#test]] (the real files).
- *(supporting, same creator)* [[artifacts/plugins/gbrain]] — a 53-skill markdown skillpack scaffold over a thin compiled gbrain CLI and a deterministic graph/vector engine — the same three-layer skeleton in the memory domain. Counted as *supporting*, not a second independent example: it is the same creator (Garry Tan), so it does not lift the count. — citation: [[sources/garrytan--gbrain#README]], [[sources/garrytan--gbrain#bin]].
- *(second creator — lifts the fat-skills half)* [[artifacts/plugins/compound-engineering]] — Kieran Klaassen / Every. The **fat-skills top** is 38 markdown skills + 43 sub-agents carrying the judgment; the **deterministic bottom** is the Bun/TypeScript converter CLI + `scripts/` + `validate-frontmatter.py`; and — exactly like gstack — the **harness is not CE's own**: the skills run *inside* Claude Code / Codex / Cursor / etc., which CE explicitly treats as interchangeable conversion targets. It even states the philosophy outright: *"Skills are guardrails for an intelligent agent, not a step-by-step controller for a non-intelligent one"* ([[sources/every--compound-engineering-plugin#plugin-AGENTS.md]]). A **different creator** demonstrating fat-skills-over-thin-harness — which weakens the "one person's house style" worry — but it does **not** resolve the bar below (the thin-harness *middle* is still un-ingested; CE rides Claude Code/Codex just as gstack rides OpenClaw). — citation: [[sources/every--compound-engineering-plugin#converter]], [[sources/every--compound-engineering-plugin#plugin-AGENTS.md]]
- *(third creator/ecosystem — further reinforces the fat-skills half)* [[artifacts/plugins/openai-codex-plugins-marketplace]] — OpenAI Codex. **479 fat markdown skills** across 56 plugins ride the Codex harness; `superpowers` (Jesse Vincent's framework) is the sharpest case — pure judgment skills (`brainstorming`, `test-driven-development`, `systematic-debugging`) with *no* deterministic substrate of their own, running on **both Codex and Claude Code** ([[sources/openai--plugins#superpowers]], [[sources/openai--plugins#skill-md]]). This is a *third independent creator* shipping fat-skills-over-interchangeable-harness — but it **does not move the promotion bar** (see note): we ingested the Codex *plugin/skill layer*, not the Codex *harness loop*, so the "~200 lines, read-only by default" middle is still taken on faith. What's new: **Codex is now named in-wiki as a harness via a concrete artifact** (previously only referenced through gstack/CE), and [[concepts/convergent-agent-plugin-spec]] explains *why* a fat-skill layer ports across harnesses at all. — citation: [[sources/openai--plugins#skill-md]], [[sources/openai--plugins#superpowers]]
- *(fourth creator — the purest "fat skills, ~zero code" instance)* [[artifacts/plugins/mattpocock-skills]] — Matt Pocock. ~17 fat markdown skills carry **100% of the capability with no deterministic substrate of its own** (the only scripts are `link-skills.sh`/`list-skills.sh`; no compiled tools, no MCP) — and they're *tiny* (`grilling` is 3 sentences, `grill-with-docs` a one-line composite). Explicitly "small, easy to adapt, and composable… work with any model," distributed by skills.sh into whichever harness you pick ([[sources/mattpocock--skills#README-philosophy]]). A **fourth independent creator** of fat-skills-over-interchangeable-harness; **does not move the promotion bar** (no harness loop ingested here either — it rides Claude Code/Codex/Cursor via skills.sh). What it sharpens: fat skills can be *tiny* as well as numerous — leverage comes from **leading words + composition**, not line count ([[artifacts/skills/writing-great-skills]]). It's also the cleanest contrast to the fat-*harness* counter-examples below: ~all top, ~no middle, ~no bottom. — citation: [[sources/mattpocock--skills#README-philosophy]], [[sources/mattpocock--skills#skill-grilling]]
- *(fifth creator/ecosystem — the harness described *from the inside*)* **Anthropic dynamic workflows** ([[concepts/dynamic-workflows]]) — Anthropic's own Claude Code team describes the harness as a generated JS file that spawns/coordinates subagents with isolated context windows. With dynamic workflows the model *writes the harness on the fly* per task, composing from 6 primitives (classify-and-act, fan-out-and-synthesize, adversarial verification, generate-and-filter, tournament, loop-until-done). This is the strongest evidence *for* "thin" yet — the harness is so thin the model can generate it. Fat skills (SKILL.md, CLAUDE.md rules) provide domain knowledge; the generated JS provides orchestration. **Caveat:** a *description* of the harness, not its source code — still no inspectable ~200-line loop. Citation: [[sources/anthropic--dynamic-workflows#how-it-works]], [[sources/anthropic--dynamic-workflows#patterns]].
- *(the first **ingested harness** — fills the missing middle, and complicates "thin")* [[artifacts/projects/eve]] — Vercel. Where Anthropic *describes* a harness, eve is one we can *read*: the wiki's first artifact where the **harness itself is the thing studied**, a framework-owned model loop + built-in toolbelt (`bash`/file/`web_*`/`todo`/`ask_question`/`agent`/`load_skill`/`connection_search`) with compaction, override-by-filename, and disable-by-sentinel ([[sources/vercel--eve#docs-default-harness]]), implemented in a real `packages/eve/src/harness/` module ([[sources/vercel--eve#packages-src]]). It **grounds the three-layer separation** cleanly — fat **Agent Skills-standard markdown** in `skills/` (`load_skill`, progressive disclosure), thin deterministic **typed tools** in `tools/` (`defineTool`, app runtime), and a generic framework-owned loop in the middle the author "never writes" ([[sources/vercel--eve#docs-skills]], [[sources/vercel--eve#docs-tools]], [[sources/vercel--eve#docs-readme-index]]). But it **refutes the literal "thin" claim**: a production harness is a *full framework* (durability, compaction, sandbox proxying, channels, discovery/compile), not "~200 lines, read-only by default." So eve answers the pattern's load-bearing open question ("is a harness ingestable, and is it thin?") with: *yes ingestable — and no, not thin.* — citation: [[sources/vercel--eve#docs-default-harness]], [[sources/vercel--eve#packages-src]], [[sources/vercel--eve#docs-readme-index]]
- *Articulation (not an artifact):* the architecture is stated outright in [[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]] and restated without metaphor — "thin harness / fat skills / fat data / fat code / interchangeable models" — in [[sources/garrytan--meta-meta-prompting#architecture]].

> **Status update 2026-06-20 — the "no harness ingested" blocker is cleared; held `proposed`, but for a sharper and now *two-sided* reason.** The promotion bar this pattern carried since creation was: *"the thin-harness middle is not ingested in any example… promotion needs an actual harness ingested so the loop's real shape (is it ~200 lines? read-only?) can be confirmed or refuted."* The middle is now attacked from **both directions**: Anthropic's own team **describes** their harness ([[sources/anthropic--dynamic-workflows]] — arguably *ultra-thin*, "so thin the model writes it on the fly"), and Vercel's [[artifacts/projects/eve]] is a **real, readable** harness ([[sources/vercel--eve#docs-default-harness]], [[sources/vercel--eve#packages-src]]) — which is a *full framework*, not "~200 lines." So the evidence is genuinely **split on the adjective**: Anthropic suggests harnesses can be vanishingly thin; eve shows a production harness is fat. The durable invariant looks less like *thin* and more like **framework-owned + generic + runs-fat-skills** (true of eve, gstack→OpenClaw, CE/Codex/mattpocock→Claude Code/Codex, and Anthropic's generated workflows alike). Current standing: **fat-skills half** cross-confirmed across **five creators** (Garry Tan, Every, OpenAI Codex, Matt Pocock, Anthropic); **harness middle** now has one *description* (Anthropic) + one *ingested instance* (eve). Likely needs reframing/renaming before promotion. Next gate: an inspectable harness *loop* (eve's `packages/eve/src/harness/`, or Claude Code's), to measure "thin" directly.

## Counter-examples or anti-pattern

- [[artifacts/plugins/anthropic-skills-marketplace]] — Anthropic's demonstration skills are **markdown-only, with no thin deterministic-code layer beneath** them. They are reference implementations meant for a human to read and learn the format, not production systems with a substrate to push execution down into. That is the *correct* choice for reference material, and it sharpens the pattern's scope: thin-harness-fat-skills is a **production-architecture** decision, not a universal one. A skill meant to be studied ≠ a system built to run.
- **The fat-harness inverse (the named anti-pattern).** The architecture's explicit failure mode is the mirror image: a *fat harness* (40+ tool definitions eating context, god-tools, a REST-wrapper-per-endpoint, 15 s generic MCP round-trips) wrapping *thin* skills — measured at "3× tokens, 3× latency, 3× failure rate," and the slow path the 75x Playwright-CLI comparison is drawn against ([[sources/garrytan--thin-harness-fat-skills#the-harness]], [[sources/garrytan--thin-harness-fat-skills#playwright-cli-75x]]). When the wrapper holds the intelligence, you forfeit the free model upgrade and pay the tax on every call.
- **gstack's own "skill OS" preamble — an internal tension with "thin."** The same artifact that exemplifies the pattern also strains it: its root `SKILL.md` is 962 lines and runs telemetry/learnings/timeline/config/routing *before any skill logic* ([[sources/garrytan--gstack#SKILL.md]]). The artifact page flags this directly — "this crosses a line… it implies gstack thinks of itself as a runtime, not a skill pack." It is a useful reminder that "thin" is an aspiration that erodes under real-world feature pressure; in practice the middle/top boundary leaks.
- [[artifacts/plugins/pm-os]] — **a deliberate fat-*behavioral*-harness, the most instructive counter-example to date.** Its 364-line workspace harness doesn't just route — it *enforces*: a mandatory pre-flight attestation block on every response, a Context Guard that refuses all work until onboarding, a deliverable gate, citation-before-opinion rules ([[sources/prodmgmt-world--pm-os-cowork#pre-flight]], [[sources/prodmgmt-world--pm-os-cowork#context-guard]]). Note the fatness is on a **different axis** than the named anti-pattern above: not tool-definition bloat (3× tokens/latency), but *behavioral rule mass* paid on every message. The product rationale is coherent — a coach-not-doer product is *made of* always-on constraints, and fat skills can't enforce what must hold before any skill fires — so this sharpens the pattern's scope the way the Anthropic counter-example does: thin-harness is an architecture for *capability* systems; products whose value **is** enforced behavior may rationally choose a fat harness and accept the rule-decay risk (which PM OS's own hook history shows is real; [[patterns/behavioral/session-start-directive]]). — citation: [[sources/prodmgmt-world--pm-os-cowork#agents-md]]

You cannot apply this pattern without first making that split.
- [[patterns/composition/resolver-routing-table]] — *composes-with:* the resolver is how the thin harness finds the *right* fat skill at the right moment ("when task type X appears, load document Y first" — [[sources/garrytan--resolvers#intro]]); it is the routing organ of the middle layer.
- [[patterns/quality-bar/skill-pack-bundle]] — *specializes:* what a *single* fat skill ships as — markdown + minimal code + a test suite (incl. resolver + resolver-eval). The skill-pack is the unit; thin-harness-fat-skills is how a library of those units is wired into a runnable system.
- [[patterns/behavioral/skill-as-method-call]] — *composes-with:* each fat skill behaves like a parameterized method call (TARGET / QUESTION / DATASET); the fat-skills layer is a library of such callables ([[sources/garrytan--thin-harness-fat-skills#skill-as-method-call]]).
- [[patterns/quality-bar/complexity-ratchet]] — *composes-with:* the forward-only quality mechanism that lets fat skills be edited safely (every session writes tests/docs/evals back), and the source of the "harness-agnostic / multiple Conductor sessions" grounding ([[sources/garrytan--complexity-ratchet#conductor-sessions]]).

## Open questions

- **Is the "thin" harness actually thin?** *Partly answered 2026-06-20 — and the answer is "not necessarily."* The first ingested harness, [[artifacts/projects/eve]], is a **full framework** (durability, compaction, sandbox proxying, channels, discovery/compile), not "~200 lines, read-only by default" ([[sources/vercel--eve#docs-default-harness]], [[sources/vercel--eve#packages-src]]). gstack's own essays already waver (#1 says ~200 lines; #6 says "a few thousand lines of routing logic" — [[sources/garrytan--meta-meta-prompting#architecture]]). The sharpened question: is "thin" a real invariant of *any* production harness, or one author's preference? Reading eve's `packages/eve/src/harness/` to measure the actual loop, and ingesting a 2nd harness, would settle it.
  - **Current scope after HumanLayer:** another inspected orchestration product is now available for comparison. Merely ingesting a second project is no longer the useful gate; identifying and comparing the loop boundaries is. Runtime bulk alone cannot confirm or refute the literal claim.
- **Does "thin" erode in practice?** gstack's 962-line root preamble suggests the middle/top layers accrete infrastructure (telemetry, learnings, routing) until "thin" stops describing the system. Is the heavy preamble a local exception or the predictable end-state of any maturing skill pack?
- **Reconcile "read-only by default" with self-rewriting skills.** The harness is "read-only by default" ([[sources/garrytan--thin-harness-fat-skills#three-layer-architecture]]) yet the `/improve` loop has the model "write rules back into the matching skills" so "the skill rewrites itself" ([[sources/garrytan--thin-harness-fat-skills#learning-loop]]). Likely reconciled by scope (read-only refers to the deterministic tools touching *your data*, not the agent editing its *own* skill markdown under approval), but the boundary should be stated explicitly wherever this pattern and [[patterns/quality-bar/complexity-ratchet]] meet.
- **Is a "harnesses / runtimes" axis missing from this wiki?** *Largely answered 2026-06-20:* the gap is now populated from two sides — [[artifacts/projects/eve]] is the first *ingested* harness (filed under `artifacts/projects/`, the runnable-but-bigger-than-one-artifact slot), and [[concepts/dynamic-workflows]] captures a harness *described from the inside* by Anthropic's own team. The *axis* exists; what's still thin is the *count* (one ingested harness vs. many fat-skill packs) and the *depth* (no harness source loop yet inspected). A dedicated `artifacts/harnesses/` axis may still be worth it once a 2nd harness lands (OpenClaw / Hermes / a Claude Code internals snapshot) to compare against eve.
  - **Current scope after HumanLayer:** [[artifacts/projects/humanlayer]] adds an inspected control-plane/runtime comparison, while external provider SDKs limit what it establishes about the underlying harness loop. A separate artifact axis remains a taxonomy choice, not a prerequisite that is resolved by counting another product.
