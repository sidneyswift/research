# complexity-ratchet

> Every agent coding session adds three things that load into the *next* session's context — (1) tests that encode what "correct" means, (2) docs that record *why*, (3) eval results that set quality thresholds — so the next agent cannot regress below them. The quality floor only rises: forward-only motion, like a socket wrench.

## Longer definition

The complexity ratchet is a **system-level** property of an agent-maintained codebase, not a single artifact. Garry Tan names the mechanism directly: every session adds *"(1) tests that encode what 'correct' means, (2) documentation of why, (3) evaluation results that set quality thresholds"*, and "the next agent loads all three into context, so it can't regress" — *"a system that can only get better, never worse"* ([[sources/garrytan--complexity-ratchet#ratchet-three-things]], [[sources/garrytan--complexity-ratchet#thesis-ratchet-free]]). It operates on *the next turn* and produces *a monotonically rising quality floor*. A creator reaches for it because AI agents made the previously-prohibitive last 20% of test coverage effectively free — agents *"don't experience effort"* and will write *"the fourteenth edge-case test… at 2am, without complaining"* ([[sources/garrytan--complexity-ratchet#effort-wall-gone]]) — so the 90% coverage that human teams stopped short of is now reachable, and 90% is where the empirical literature puts the *"knee"* in defect-removal efficiency ([[sources/garrytan--complexity-ratchet#90pct-coverage-data]]).

Crucially, the ratchet reframes coverage from a vanity metric to a **proxy** for *"how much of the system's behavior is under contract"* ([[sources/garrytan--complexity-ratchet#coverage-as-contract-proxy]]). Each test locks in a specific lesson learned — holder-confusion, weight-rounding, the interactive-review gate — and those tests *"survive employee turnover"* because *"the agent's context window doesn't quit"* ([[sources/garrytan--complexity-ratchet#tests-as-institutional-memory]]). The ratchet works *even when the human isn't at their best* (a new contributor, a model-version change, coding at 2am) precisely because the check is on the next turn, not the person. Skip it and a vibecoded project becomes *"a haunted house where every change breaks something"* by v0.5 — *"AI coding works fine. They just didn't build the ratchet."* ([[sources/garrytan--complexity-ratchet#vibecoding-death]]).

## Mechanism

The ratchet is built from three deposits per session — tests, docs, evals — each of which becomes load-bearing context for the next agent. The two Garry Tan repos in this wiki show all three as real files.

**The deposit loop (per session):**

1. A failure or a new behavior is observed.
2. The agent (or human) writes a **test that pins the correct behavior**, a **doc that records why**, and where the output requires judgment, an **eval with a threshold**.
3. All three land in the repo. On the next session the agent loads them as context, and CI fails if a change drops below the floor. The floor never falls — it only ratchets up.

**gstack — "everything harnessable is testable."** The strongest demonstration is that the test surface extends to interactions that traditionally *had no test surface at all*. gstack's interactive plan-review contract is tested **at the TTY level** ([[sources/garrytan--complexity-ratchet#tty-interactive-review-test]]): a real-PTY harness spawns Claude Code in a pseudo-terminal and **fails if the agent reaches the terminal state without firing an interactive question**. The real files:

- `test/extension-pty-inject-invariant.test.ts` — a static invariant enforcing that every `gstackInjectToTerminal` call is preceded by an `await gstackScanForPTYInject` (the PTY-injection safety the harness depends on).
- `test/skill-e2e-plan-{ceo,eng,design,devex}-finding-floor.test.ts` — the **floor tests**. `skill-e2e-plan-eng-finding-floor.test.ts` seeds a "forcing finding" and asserts the agent fires *at least one* `AskUserQuestion`; the failure message reads *"regression — agent reached terminal without firing AskUserQuestion."* This is a behavioral contract turned into a runnable gate.
- `plan-eng-review/SKILL.md` — the ratchet's *prose* response to the same bug: STOP gates ("At a STOP point, stop immediately"), anti-rationalization clauses, and the **anti-shortcut clause** (verbatim): *"The plan file is the OUTPUT of the interactive review, not a substitute for it… this is the precise failure mode of the May 2026 transcript bug."* The doc and the floor test pin the *same* lesson from two sides.

Underneath sits the **multi-tier harness** the essay's "harnessable is testable" claim describes ([[sources/garrytan--gstack#test]]): `skill-validation.test.ts` (Tier-1, deterministic, free), `skill-e2e-*.test.ts` (Tier-2 end-to-end via `claude -p`), `skill-llm-eval.test.ts` (Tier-3 LLM-as-judge). A `gate`/`periodic` split (CI-blocking vs. weekly cron, declared in `test/helpers/touchfiles.ts`) keeps the expensive tiers economically runnable — that split is *what makes the ratchet affordable to crank on every PR*. And `scripts/slop-diff.ts` plus `docs/designs/SLOP_SCAN_FOR_REVIEW_SHIP.md` wire Ben Vinegar's third-party `slop-scan` into the ship gate; gstack scored **5.24** ("the worst he'd measured at the time") and Garry *"cut the score by 62% in one session"* ([[sources/garrytan--loc-controversy#slop-scan]]) — a quality floor that, once raised, the gate holds.

**gbrain — the documented-failure-locks-a-test loop.** gbrain's epistemological extraction pulled **100,720 claims** across **28,000 pages**, scored **6.8/10** by a cross-model (GPT-5.5 + Claude) eval; **holder confusion** — *who* holds a belief (author / person quoted / the system's inference engine) — was wrong **35% of the time in v1**; v2 fixed 6 failure modes, enforced weight-rounding **at the DB layer**, and **locked 17 tests** so no future version can ship without them ([[sources/garrytan--complexity-ratchet#gbrain-extraction-ratchet]]). The grounding doc is `docs/takes-vs-facts.md`, whose own scorecard records *"Attribution: 6.5 — Holder/subject confusion was #1 issue"* and codifies the fix as a rule (*"Holder ≠ subject"*). The companion `docs/contradictions.md` and the migration tests (`test/migration-orchestrator-v0_31_0.test.ts`) are the doc-and-test deposits of later sessions ([[sources/garrytan--gbrain#docs-takes-vs-facts]]). The reachability arm of the same discipline ships as `src/commands/check-resolvable.ts` and the filing-rules contract as `skills/_brain-filing-rules.md`. Each is a lesson made permanent — *"every bug becomes a test that lives forever"* ([[sources/garrytan--skillify-manifesto#big-idea]]).

The behavioral engine that *fills* the ratchet is the self-rewriting skill loop: the agent *"proposes new rules and writes them back into the matching skills… the skill rewrites itself"* ([[sources/garrytan--thin-harness-fat-skills#learning-loop]]), so each session leaves the next one a higher floor — *"every skill you write is a permanent upgrade… it never degrades"* ([[sources/garrytan--thin-harness-fat-skills#permanent-upgrades]]). And the affordability claim is stated outright: *"testing at multiple levels is what makes AI-assisted coding actually work… without those layers, you're just generating confident garbage at high speed"* — tests went from ~100 in January to **2,000+**, with *"a coverage audit in every gstack PR body"* ([[sources/garrytan--loc-controversy#testing-is-the-unlock]]). The coverage audit *is* the ratchet, made visible per PR.

## When to use

- **Any agent-maintained codebase you intend to keep changing.** The ratchet is precisely what makes fast iteration *safe* — it converts "did this edit break something?" into a runnable, blocking question rather than a hope.
- **Multi-contributor or multi-model projects.** Tests catch regressions regardless of *who or what* wrote the change. *"A new contributor doesn't need to understand the whole system. They need to make the tests pass"* ([[sources/garrytan--complexity-ratchet#proof-of-concept-contributors]]); the floor holds across a model-version bump because the check is on the next turn, not the person ([[sources/garrytan--complexity-ratchet#ratchet-not-the-person]]).
- **Behaviors that previously had no test surface** — TTY interactions, agent protocols, OS/process/cron state, browser button-states, API schemas. The expansion claim is the whole unlock: *"If you can harness it… observe it… assert on it… you can ratchet it"* ([[sources/garrytan--complexity-ratchet#everything-harnessable-testable]]). gstack's TTY floor tests are the proof of concept.
- **Single-author / solo projects too.** For a one-person project, *"tests are the only institutional memory you have"* ([[sources/garrytan--complexity-ratchet#tests-as-institutional-memory]]) — the ratchet substitutes for the team knowledge you don't have.

## When NOT to use

- **Throwaway / one-shot code.** If you'll run it once and discard it, the ratchet is pure overhead — there is no "next session" to protect.
- **The genuinely-hard-to-test 10%.** The essay explicitly carves this out: line coverage is a proxy, and the remaining *"integration / infra / genuinely-hard"* slice is *fine* to leave uncovered ([[sources/garrytan--complexity-ratchet#coverage-as-contract-proxy]]). Chasing 100% (the disproportionately expensive last stretch human teams correctly stopped at — [[sources/garrytan--complexity-ratchet#effort-wall-gone]]) trades real cost for diminishing safety.
- **When you'd be building a cage, not a ratchet.** This is the sharp one and the actual test of understanding. Tests that encode *behavioral contracts* (the holder-confusion test, the weight-rounding rule, the interactive-review floor) are the ratchet. Generic "distrust the model" scaffolding — validators, sanitizers, retry-loops, a 1,778-line fact-checker bolted on to *police* a capable model — is the **"Foxconn factory"** the *same author* warns against ([[sources/garrytan--foxconn-factories#thesis]], [[sources/garrytan--foxconn-factories#factory-audit]]). Same word ("tests"), opposite spirit. If your "ratchet" is mostly defensive code written because you don't trust a worker who can already do the job, you've crossed the line; fix the altitude before adding tests around it.

## Why it works

The underlying principle is an **economic** one stacked on a **context-window** one. Economically, the cost curve that made 90% coverage prohibitive for human teams collapsed: the last 20% of coverage *"costs disproportionately more, which is why human teams stopped at 70-80%,"* but *"AI coding agents don't experience effort"* — so verification that was *"previously too expensive to sustain"* is now free ([[sources/garrytan--complexity-ratchet#effort-wall-gone]]). And 90% is not arbitrary: across >10,000 projects, defect-removal efficiency jumps from ~65-75% to **92-97%** as coverage crosses an ~85% *knee* — *"going from 70% to 90% coverage isn't 30% better. It's an order of magnitude fewer escapes"* ([[sources/garrytan--complexity-ratchet#90pct-coverage-data]]).

Mechanically, the ratchet exploits *how agents load context*. Because the tests, docs, and eval thresholds are files in the repo, the next agent reads them as authority on the next turn — so the floor is enforced *structurally*, independent of who is at the keyboard or which model version is running ([[sources/garrytan--complexity-ratchet#ratchet-not-the-person]]). This is also why it doubles as institutional memory: *"// DO NOT CHANGE THIS — ask Dave"* and Dave left three years ago, but *"the agent's context window doesn't quit"* ([[sources/garrytan--complexity-ratchet#tests-as-institutional-memory]]). The defense against the obvious "coverage is a vanity metric" objection is built in: coverage is a *proxy for behavior-under-contract*, so at 90% *"nearly every behavior change trips a test signal"* and each test *"locks in a specific lesson learned"* ([[sources/garrytan--complexity-ratchet#coverage-as-contract-proxy]]). The ratchet, in short, is what turns the [[patterns/quality-bar/skill-pack-bundle]] discipline (tested artifacts) into a forward-only *system property* (a floor that only rises).

## Detection recipe

A falsifiable test for spotting the ratchet (`## Examples` are the positive fixtures; the vibecoded-collapse and Foxconn-factory cases are the negative test):

- **Look for**: a per-session deposit of (1) tests pinning correct behavior, (2) docs recording *why*, (3) eval thresholds — that load into the *next* session's context; a CI gate / branch protection blocking merges below the floor; a knowledge store (e.g. `docs/solutions/`) future agents are explicitly pointed at.
- **Confirm with**: the floor is enforced **structurally** — a later session/agent/model *cannot* regress below it (a blocked PR, a required failing check) — and each test encodes a *specific lesson* (a fixed bug like holder-confusion), with coverage treated as a proxy for behavior-under-contract.
- **Rule out**: throwaway/one-shot code (no "next session" to protect); chasing the genuinely-hard last 10% / 100% coverage; and the sharp one — the **Foxconn factory**: validators/sanitizers/retry-loops/fact-checkers written to *police* a capable model rather than pin behavioral contracts. Same word ("tests"), opposite spirit — that's the cage, not the ratchet.

## Examples in this wiki

- [[artifacts/plugins/gstack]] — **the TTY interactive-review floor + multi-tier harness + slop-scan gate.** The interactive plan-review contract is ratcheted at three layers that pin the same lesson: the `skill-e2e-plan-*-finding-floor.test.ts` floor tests (fail if the agent reaches terminal without firing `AskUserQuestion`), the PTY-injection invariant (`test/extension-pty-inject-invariant.test.ts`), and the STOP-gate / anti-shortcut prose in `plan-eng-review/SKILL.md` (*"the plan file is the OUTPUT of the interactive review, not a substitute for it"*). The `gate`/`periodic` tier split keeps the expensive evals runnable; slop-scan is wired into the ship gate (5.24 → cut 62% in one session). — citation: [[sources/garrytan--complexity-ratchet#tty-interactive-review-test]], [[sources/garrytan--complexity-ratchet#everything-harnessable-testable]], [[sources/garrytan--gstack#test]]
- [[artifacts/plugins/gbrain]] — **the documented-failure-locks-a-test loop.** The extraction pipeline scored 6.8/10; holder confusion was wrong 35% in v1; v2 fixed 6 modes, enforced weight-rounding at the DB layer, and **locked 17 tests** so no later version can ship without them — the floor made permanent. Grounded in `docs/takes-vs-facts.md` (its scorecard records *"Holder/subject confusion was #1 issue"* and codifies *"Holder ≠ subject"*), `docs/contradictions.md`, and the migration tests. — citation: [[sources/garrytan--complexity-ratchet#gbrain-extraction-ratchet]], [[sources/garrytan--gbrain#docs-takes-vs-facts]]
- [[artifacts/plugins/compound-engineering]] — **the independent, non-Garry example that confirms the pattern**, and the one that names it from the *knowledge* side rather than the *test-coverage* side. The forward-only floor here has two arms: (1) a **knowledge ratchet** — `/ce-compound` writes every solved problem into `docs/solutions/` (30 docs, dogfooded) with a Discoverability Check that edits the project's instruction file so future agents *find* the store, and a dedup rule that *updates* an overlapping doc rather than letting two drift apart; and (2) a **test/CI floor** — branch protection on `main` *requires* the `test` check, so a later session **structurally cannot merge below the floor** (the "blocked PR" the promotion bar asked for), with behavioral contract tests (`review-skill-contract`, `pipeline-review-contract`) pinning skill behavior. Kieran Klaassen arrived at the same forward-only principle independently (["compound engineering"](../../concepts/compound-engineering.md): "each unit of work should make the next easier"), which is exactly the evidence that distinguishes "a general property of agent-maintained code" from "Garry Tan likes tests." — citation: [[sources/every--compound-engineering-plugin#docs-solutions]], [[sources/every--compound-engineering-plugin#release-automation]], [[sources/every--compound-engineering-plugin#tests]]

> **Confirmed 2026-06-02 — the same-creator caveat is retired.** The two Garry Tan examples (gstack, gbrain) rest on overlapping test-evidence and one house style; [[artifacts/plugins/compound-engineering]] supplies what the old promotion bar named explicitly: a **non-Garry codebase** where a later session **structurally cannot regress** below a prior floor (branch protection blocks the merge), *and* an **independent naming** of the principle ([[concepts/compound-engineering]]) that confirms the ratchet is a field-level idea, not one builder's habit. Note the remaining nuance: Kieran is *also* test-heavy (~1,094 cases), so CE doesn't fully test the "non-test-maximalist" edge — but its **knowledge ratchet** (`docs/solutions/` populated by `/ce-compound`) is a *distinct mechanism* from gstack's test-floor, which is itself fresh evidence that the ratchet generalizes beyond "more tests."

## Counter-examples or anti-pattern

- **Vibecoded projects that skip the ratchet** — the essay's own foil. Projects with no tests/docs/evals *"fall apart at moderate complexity,"* becoming *"a haunted house where every change breaks something"* by v0.5. The diagnosis is pointed: the AI coding wasn't the problem — *"they just didn't build the ratchet"* ([[sources/garrytan--complexity-ratchet#vibecoding-death]]). This is the *absence* case: same agents, same models, no forward-only floor, predictable collapse.
- **The Foxconn factory — the same test corpus, opposite valence.** The inverse failure is *over*-building. Essay #8's self-audit frames gbrain's **~276K lines of tests** (more test code than app code) pejoratively as a *"Foxconn factory"* — code written *"to police"* a capable model ([[sources/garrytan--foxconn-factories#factory-audit]], [[sources/garrytan--foxconn-factories#thesis]]). Essay #7 celebrates that *same* growing test mass as the ratchet working ([[sources/garrytan--complexity-ratchet#proof-of-concept-contributors]]). The two essays use the **same number with opposite valence** — and the reconciliation *is the pattern's boundary*: tests that encode behavioral **contracts** are the ratchet; tests that exist only to distrust a capable worker are the cage. The carve-out the author himself draws ([[sources/garrytan--complexity-ratchet#coverage-as-contract-proxy]]) is the line. **Flagged for the synthesis** — the contradiction is already tracked on both source pages ([[sources/garrytan--complexity-ratchet#root]]) and is the cleanest single illustration of where this pattern stops being good.

## Related patterns

- [[patterns/quality-bar/skill-pack-bundle]] — **specializes / unit-of**: the skill-pack bundle is the *unit* (a single tested skill: markdown + code + unit test + LLM eval + E2E + resolver + resolver eval); the complexity ratchet is the *system property* that a repo full of those bundles produces — a forward-only quality floor. Closely related and easy to conflate (see Open questions); cross-linked deliberately.
- [[patterns/behavioral/latent-vs-deterministic-split]] — **enables**: the deterministic side of the split is exactly what you can assert on. "Everything harnessable is testable" is the ratchet's restatement of "the deterministic half is the testable half" ([[sources/garrytan--complexity-ratchet#everything-harnessable-testable]]).
- [[patterns/structural/thin-harness-fat-skills]] — **composes-with**: skills authored as fat markdown are *permanent, ratcheting upgrades* — the self-rewriting `/improve` loop writes new rules back into the skill so the next run starts higher ([[sources/garrytan--thin-harness-fat-skills#learning-loop]], [[sources/garrytan--thin-harness-fat-skills#permanent-upgrades]]).
- [[patterns/composition/resolver-routing-table]] — **contributes**: resolver trigger evals and the `check-resolvable` reachability audit are themselves *floor tests* — they ratchet the routing layer (a skill that exists but can't be reached is a "dark" capability the audit blocks).

## Open questions

- **Is complexity-ratchet truly distinct from [[patterns/quality-bar/skill-pack-bundle]], or two views of one tested-artifact discipline?** Best current answer: unit (one tested skill) vs. system (the forward-only floor a repo of them produces). But they cite overlapping evidence and the boundary is thin — a future LINT pass should decide whether they stay separate or merge.
- **Does the forward-only floor hold in a codebase NOT built by a test-maximalist?** *Partly answered (2026-06-02):* [[artifacts/plugins/compound-engineering]] is a **non-Garry** project where a later session is structurally unable to regress (branch protection blocks the merge) — clearing the "independent witness" half. The remaining gap: Kieran is *also* test-heavy (~1,094 cases), so the "non-*test-maximalist*" edge is still untested. A vibecoded-but-ratcheted project by a non-maximalist would close it fully.
- **Is 90% a real knee for *agent behavior contracts*, or borrowed from traditional-code research?** The 85-90% knee comes from Capers Jones / DO-178C defect-removal data on *conventional* code ([[sources/garrytan--complexity-ratchet#90pct-coverage-data]]). Whether the same threshold governs *behavioral* contracts on non-deterministic agent outputs (LLM-as-judge evals, resolver routing) is an extrapolation the essay makes but does not separately evidence.
- **Where exactly is the ratchet/cage line?** The Foxconn-factory tension (same 276K-test number, opposite valence) shows the boundary is real but unstated as a rule. A synthesis note quantifying "contract test vs. distrust scaffolding" would sharpen *When NOT to use* and resolve the cross-essay contradiction the wiki already tracks.
